# 大题目准备

适用场景：约两小时、一个主题、需要交付可运行程序的 C++ OA / coding task。以 DRW 准备和 Headlands Disaster Recovery 复盘为背景。

整理日期：2026-10-16。代码示例以 C++17 为基线。具体题目、编译器、编辑器和允许使用的资源，以面试方说明为准。

## 1. 考前速查

### 开始写代码之前

- [ ] 我能用一分钟完整复述输入含义、核心规则、失败条件、查询和输出。
- [ ] 我知道哪些规则会改变数据模型，哪些只是实现细节。
- [ ] 我能手算一个正常例子和两三个能区分不同理解的例子。
- [ ] 我已经列出全部必需功能，并把 Bonus 单独标记。
- [ ] 我知道主要阶段的输入、输出和执行顺序。
- [ ] 我估算过时间、空间复杂度，确认没有明显超出约束。

### 实现与调试期间

- [ ] 每完成一个小模块就编译，尽早打通一个最小端到端案例。
- [ ] 原始输入、解析结果、状态变化、查询结果可以分别观察。
- [ ] 日志带 line / step / ID，能定位第一次错误更新。
- [ ] 维护关键不变量；昂贵的全量检查只在调试时开启。
- [ ] 无效输入先完整判定，再决定是否修改状态。
- [ ] 修复的 bug 都留下一个最小回归测试。

### 最后提交之前

- [ ] 编译运行的是最新代码。
- [ ] 必需功能全部完成，特别是全局失败条件。
- [ ] 检查端点、tie-break、空结果、换行和空格要求。
- [ ] 检查多组输入或多次函数调用之间没有残留状态。
- [ ] 关闭日志、随机对拍和昂贵的全量校验。
- [ ] 保留题目要求的入口、签名和退出行为。

## 2. 两小时单题可能是什么

两小时只是时间上限，不能据此确定题目数量、难度或类型。一道题也可能包含多个阶段、多个函数以及追加要求。

对当前准备更有价值的形式：

| 类型 | 合适的练习范围 | 工作量来源 |
| --- | --- | --- |
| 规则模拟 | 俄罗斯方块、事件模拟、简化撮合 | 多条规则相互作用、状态更新与边界 |
| 数据关联与查询 | repository recovery、日志归并、区间查询 | 解析、建模、算法组合、排序、查询 |
| 图算法完整应用 | 动态连通性、依赖关系、调度 | 把规则转成图，处理全局约束 |
| 数据处理组件 | binary stream decoder、订单簿 | buffer / 索引 / 状态的一致性 |
| 现有程序修复与优化 | 读代码、修 bug、降低复杂度、补测试 | 理解语义、保持行为、验证修改 |

标准 LRU / LFU、基础 SPSC queue 的单独实现，当前准备优先级较低；有追加要求或现成框架时仍可能成为长任务。MPMC / 通用 lock-free queue 可以很难，不能用代码量或时长简单排除。

基础静态岛屿数量题通常适合作为算法专项；动态增加陆地、大规模输入、附加查询等变体，可以发展成完整任务。这些是练习设计，不是对 Jump 原题的还原。

### 面经证据与预测分开看

| 公司 | 已查到的公开记录 | 不能据此确定的部分 |
| --- | --- | --- |
| DRW | 俄罗斯方块落块序列计算高度；另有新加坡两小时 challenge 和英国两小时 take-home 记录 | 当前团队是否考方块、是否单题、是否 review 本次代码 |
| Jump | 优化题、字符串处理、多题 Codility，以及独立 homework 的记录 | 十多年前岛屿题的具体规格和当前题型 |
| HRT | 官方说明包含 coding、debugging、technical design | 两小时单题的具体内容 |
| Tower | 候选人报告缓存设计后追加可选策略；另一轮为 Shortest Bridge | 该记录不是两小时独立任务 |
| Citadel Securities | 候选人报告阅读复杂 C++ 并优化 | 原帖没有清楚确认正式限时和完整规格 |

匿名面经只说明有人报告过某种形式。针对本次 DRW 优先练完整任务，是中等置信度的准备判断；具体押题的置信度较低。

## 3. Headlands 复盘：开工前先形成完整模型

### 3.1 当时的过程与风险

当时的回忆：没有完全理解题目就先写 parser，再写 DSU，之后反复回读题目、编写主逻辑，最后匆忙补 ambiguity。

可以概括为：每看懂一个局部就实现一个局部，整体解法较晚才闭合。parser 和 DSU 有可见进展，但后续需求不断进入，增加了返工和时间压力。

这是基于回忆的流程判断，置信度为中；没有当时代码和阶段耗时，不能据此断言各模块本身写得慢。

写 parser 本身合理。开工前应先明确它属于哪条完整处理路线，以及后续阶段需要哪些信息。

### 3.2 这道题的需求清单

以下依据提供的重建题面；它不能替代真实考试中的原始题面。

| 需求 | 必须明确的语义 |
| --- | --- |
| repository 归属 | 相同 `(path, opaqueId)` 建立关联，再取传递连通关系 |
| 建立关联的数据范围 | 全部有效 commits，不能先按查询时间过滤 |
| 查询定位 | 用 `(path, opaqueId)` 找到所属 repository |
| 查询返回 | 该 repository 在时间范围内的所有 commits，不只是包含指定文件的 commits |
| ambiguity | 同一归并结果内，某路径存在冲突的 opaque ID |
| 全局失败 | 任意 repository 有 ambiguity，整个输出只有 `AMBIGUOUS INPUT!` |
| 排序 | `(timestamp, commitId)` 升序 |
| 时间范围 | 包含两端点 |
| 空结果 | 输出空行 |
| 格式 | 非空结果行有题面规定的尾随空格 |
| malformed | 重建题面把严格识别并丢弃标为 Bonus；被丢弃的行不能污染状态 |
| 退出 | 重建题面要求包括 ambiguity 在内均正常退出，状态码为 0 |

题面关于反向映射的 “and vice-versa” 应列为需要确认的语义。明确给出的冲突例子是同一 repository 内相同路径对应不同标识；不要把对含糊文字的额外推断当作已确认规则。

**Ambiguity 是核心语义；严格 malformed 检测才在重建题面里标为 Bonus。** 优先级依据题面定义，不依据实现是否熟悉或代码是否短。

### 3.3 一分钟口述解法

> 解析有效日志，用相同文件标识关联 commits。全部归并完成后，检查每个分量是否存在冲突；若有，输出全局错误。否则建立各 repository 按时间和 ID 排序的 commit 列表。查询时先定位 repository，再检索闭区间内的 commits，按要求输出。

能讲清上述路线后，再进入局部实现。无需预先决定每个循环和辅助函数的写法。

### 3.4 最有区分力的小测试

| 测试 | 要检验的理解 |
| --- | --- |
| 同路径不同 ID，但处于不连通的分量 | 不能仅凭路径相同判冲突 |
| A 连 B、B 连 C，A/C 对某路径给出不同 ID | 冲突可能通过传递归并才出现 |
| 桥接 commit 位于查询时间范围外 | 建立 repository 时仍必须使用它 |
| 一个分量冲突，查询另一个正常分量 | 仍然只输出全局错误 |
| timestamp 相同、commit ID 不同 | tie-break 正确 |
| 时间恰好等于查询起点或终点 | 闭区间正确 |
| 查询文件不存在、范围内无 commit | 空行正确 |
| malformed 行本可建立一条连接 | 丢弃后不能留下 union 或索引副作用 |

### 3.5 阶段路线与数据保留

1. 解析、验证日志，保留后续阶段所需数据。
2. 根据相同文件 key 完成 DSU 归并。
3. 按最终分量检查冲突。
4. 建立每个分量的排序索引。
5. 定位查询所属分量并执行范围查询。
6. 格式化输出。

先完成全部 union，再做独立冲突检查，是容易写对的一种实现选择。若选择边 union 边维护映射，就必须正确合并分量元数据，增加了实现要求。

对于规模上界，还要估算文件关联数量、字符串和哈希表节点的实际内存。不要把“保存全部信息”理解为无条件保留多份原始文本、tokens 和重复字符串。ID / timestamp 的类型按题面数值范围选择，不能随手使用 `int`。

## 4. 读题与开工规则

### 4.1 两遍读题，各有产物

第一遍建立全貌：输入含义、核心关系、查询对象、输出、全局失败条件和约束。

第二遍补实现契约：精确格式、数值范围、排序、边界、无结果、多组输入和 Bonus。

后续回读带着具体问题，例如“上界是否包含”或“查询是否返回整个分量”。避免每次重新从头恢复整个题意。

### 4.2 区分结构性问题与局部细节

| 开写前必须解决 | 可以实现时逐步解决 |
| --- | --- |
| 节点、关系、状态分别是什么 | parser 内部用哪种拆分方式 |
| 查询操作作用于哪个集合 | 辅助函数如何命名 |
| 哪些条件导致全局失败 | 调试信息具体格式 |
| 是否需要完整输入才能确定结果 | 某个循环的局部写法 |
| 时间、空间复杂度是否可行 | 合理的初始 reserve 值 |

### 4.3 每个核心需求必须有位置

维护一个简短清单，允许尚未实现，但不能没有记录：

- [ ] 正常输入与解析
- [ ] 核心关联 / 状态更新
- [ ] 全局校验与失败行为
- [ ] 索引与查询
- [ ] 排序、端点、空结果、输出格式
- [ ] Bonus

初始骨架应能体现所有必需阶段。尽早编译，然后逐步完成可验证的最小路径；全局规则已经进入设计，即使具体实现稍后完成，也不再属于临时补漏。

## 5. 专项练习

| 专项 | 练习内容 | 关键边界 |
| --- | --- | --- |
| 按行读取 | `getline`、空行、多组输入、EOF | 最后一行没有换行；与 `operator>>` 混用 |
| token 拆分 | 空白、逗号、key-value pairs | 连续分隔符、空字段、缺字段、多字段 |
| 数字解析 | 64 位、符号、范围、完整消费 | 空串、溢出、负数、`123abc` |
| 命令解析 | 文本转 `Command`，验证后执行 | 未知命令、重复 ID、对象不存在 |
| 状态更新 | 插入、删除、移动、合并、消除 | 部分更新、更新顺序、多索引一致性 |
| 二维模拟 | 坐标转换、碰撞、落块、消行 | 四个边界；连续删除；坐标正方向 |
| 排序与查询 | 多字段排序、二分、闭区间 | 同值 tie-break；空集合；区间端点 |
| 输出 | 精确文本、棋盘、图、状态快照 | 空格、换行、确定顺序、上下方向 |
| 测试设计 | 边界、状态转移、回归、对拍 | 少量能区分错误理解的案例 |

打印图形优先练内部状态：带行列号的棋盘、邻接关系、分量归属、分组后的 commits、事件执行记录。

### 5.1 输入处理的提交边界

先解析到临时对象，完成格式和语义校验，再修改主状态。若某条输入被判定无效，不能遗留部分索引更新或 DSU 连接。

题面保证合法的部分，直接依赖其契约；题面要求拒绝或跳过的部分，明确实现。不要自行增加错误处理规则。

### 5.2 一个严格数字字段解析模板

```cpp
#include <charconv>
#include <optional>
#include <string_view>
#include <system_error>
#include <type_traits>

template <class Integer>
std::optional<Integer> parse_integer(std::string_view s)
{
    static_assert(std::is_integral_v<Integer>);
    static_assert(!std::is_same_v<std::remove_cv_t<Integer>, bool>);

    if (s.empty()) {
        return std::nullopt;
    }

    Integer value{};
    const char* first = s.data();
    const char* last = first + s.size();
    const auto [ptr, ec] = std::from_chars(first, last, value);

    if (ec != std::errc{} || ptr != last) {
        return std::nullopt;
    }
    return value;
}
```

`from_chars` 不跳过前导空白，整数解析不接受前导 `+`；无符号目标不接受 `-`。是否要支持这些形式，由题面决定。检查 `ptr == last` 才能拒绝 `123abc` 一类合法前缀后跟垃圾字符的输入。范围错误由目标类型决定。

### 5.3 容易浪费时间的细节

- `cin >> n` 后直接 `getline` 可能先读到剩余换行；明确处理，不盲目用 `std::ws` 吃掉可能有意义的空白或空行。
- 若只允许单个空格分隔，`istringstream >> token` 会宽松接受多种空白，不能代替严格格式验证。
- `string_view` 不拥有数据，不能长期保存指向不断覆盖的输入行的 view。
- `vector` 扩容或删除可能使指针、引用、迭代器失效。
- 二维坐标常使用有符号临时值表达 `-1`；先检查合法性，再转为容器下标。
- `unordered_map::operator[]` 会插入缺失 key；只想查询时优先 `find`。
- 比较器要满足严格弱序；不要把 `<` 写成 `<=`。
- 删除元素时，明确下一次迭代的位置，防止跳过连续待删除项。
- 整数乘法应在运算前扩大类型，并估算扩大后的类型是否仍可能溢出。

## 6. 最小调试工具箱

### 6.1 CHECK / LOG / DUMP

```cpp
#include <cstdlib>
#include <iostream>

bool enableLog = false;

#define CHECK(expr)                                           \
    do {                                                      \
        if (!(expr)) {                                        \
            std::cerr << __FILE__ << ':' << __LINE__           \
                      << ": CHECK(" #expr ") failed\n";        \
            std::abort();                                     \
        }                                                     \
    } while (false)

#define LOG(msg)                                              \
    do {                                                      \
        if (enableLog) {                                      \
            std::cerr << msg;                                 \
        }                                                     \
    } while (false)

#define DUMP(x) LOG(#x << " = " << (x) << '\n')
```

```cpp
CHECK(index < values.size());
LOG("step=" << step << " id=" << id << '\n');
DUMP(parent[u]);
```

使用约定：

- `do ... while(false)` 使语句宏可以安全放入 `if/else`。
- `CHECK` 失败打印文件、行号、表达式，并停止本次运行；主要用于内部不变量与自测。
- 正常答案走 `cout`，调试走 `cerr`；不假设平台一定展示 stderr。
- 关闭 `LOG` 后，其中表达式不求值；程序行为不能依赖日志中的副作用。
- `CHECK` 本例始终执行；标准 `assert` 可能被 `NDEBUG` 禁用。两者都不要隐藏必要业务操作。
- 题面定义的无效输入或 ambiguity，应输出规定结果；不能拿调试用 `abort` 代替正常错误路径。
- 频繁日志可能显著拖慢程序。优先缩小追踪范围，提交前关闭。
- 宏参数中若直接出现逗号表达式或花括号初始化列表，注意预处理器参数划分；复杂表达式先写成局部变量。

最初的 `enableLog && std::cout << ...` 在常见用法下可以利用短路工作。这里统一采用 `LOG(msg)`，让调用形式和语句边界更明确。

### 6.2 递归进入与返回

下面片段放在递归函数内部，`depth` 通过参数传递，子调用使用 `depth + 1`：

```cpp
const std::string indent(depth * 2, ' ');
LOG(indent << "enter u=" << u << '\n');

// 递归计算……

LOG(indent << "leave u=" << u
           << " result=" << result << '\n');
```

进入日志显示当前参数，返回日志显示计算结果。避免全局 depth 在早退或异常路径上没有恢复。

### 6.3 分阶段观察与逐事件校验

```cpp
LOG("line=" << lineNo << " raw=[" << line << "]\n");
LOG("step=" << step << " command=" << commandName
    << " size_before=" << before
    << " size_after=" << after << '\n');
```

观察顺序：原始输入、解析对象、每条指令后的状态、查询结果、最终输出。目标是找到第一次偏离预期的更新。

准备普通辅助函数即可：`dump_board`、`dump_graph`、`dump_state`、`validate_state`。不要把练习重心转成开发日志框架。

| 场景 | 不变量例子 |
| --- | --- |
| 棋盘 | 格子值合法；缓存高度等于扫描结果 |
| DSU | 成功合并不同分量时，分量数减少一 |
| 订单簿 | 价位总量等于该价位订单剩余量之和 |
| 多索引结构 | 主容器与 ID 索引包含同一批有效对象 |
| 被丢弃的命令 | 执行前后主状态一致 |

昂贵的全量检查只在调试阶段开启，不能让最终查询复杂度因验证代码而退化。

## 7. 自测方法

### 7.1 局部函数自测

直接验证 parser、排序、查询、状态变换等函数，避免所有问题都只能通过完整输入定位。

例如 `parse_integer<std::int64_t>` 可测空串、负数、类型边界、溢出和尾部垃圾；非负字段再根据契约使用无符号目标或单独校验符号。

### 7.2 完整程序：stream 注入

若题目要求完整程序，可以把逻辑入口写为：

```cpp
void solve(std::istream& in, std::ostream& out);
```

实现 `solve` 后，使用下面的辅助函数；它依赖前面的 `CHECK`：

```cpp
#include <sstream>
#include <string>

void check_case(const std::string& input,
                const std::string& expected)
{
    std::istringstream in(input);
    std::ostringstream out;
    solve(in, out);

    const auto actual = out.str();
    if (actual != expected) {
        std::cerr << "input: [" << input << "]\n"
                  << "expected: [" << expected << "]\n"
                  << "actual: [" << actual << "]\n";
    }
    CHECK(actual == expected);
}
```

这能同时检查输入、计算和格式。方括号便于观察边界；若空白差异仍不明显，再打印字符串长度或转义后的 `\n`、`\t`、`\r`。

本地可用 `LOCAL_TEST` 选择测试入口与正常入口；是否有此编译开关取决于环境。不要从 `solution()` 调用一套又反过来调用 `solution()` 的测试，造成递归执行。

### 7.3 平台提供函数签名

若题目提供 `solution(...)`，保留签名和平台入口，拆出可测试的计算函数。优先使用平台自定义测试，不自行增加冲突的 `main()`。

Codility 官方说明允许添加自己的测试用例，但具体入口和运行方式取决于任务模板。样例运行成功不代表隐藏测试全部通过。

### 7.4 慢参考实现、对拍与回归

- 对小输入写一个直观但较慢的参考实现，与优化实现比较。
- 参考实现应尽量采用独立思路，避免复制同一个错误。
- 随机种子固定；失败时打印种子和完整输入。
- 缩小失败输入，删除无关指令或节点，直到能直接解释错误。
- 将最小失败例子保留为回归测试，修复后再跑。
- 适用时检查性质：只读查询不改变状态；格式上无关的输入排列是否应保持结果，要以题面语义为准。

### 7.5 一组通用测试维度

- 最小规模、空集合、单元素。
- 全部相同、全部不同、重复操作。
- 值恰好在边界、刚好越界。
- 同值排序、相同 timestamp 的确定次序。
- 连续删除、多次合并、状态从空到非空再到空。
- 无结果、未知 key。
- 连续多组输入、同一函数多次调用。
- 数据量增长后的时间和内存表现。

## 8. Codility 与本地工具

### 8.1 不默认有完整 IDE

截至本次查询，Codility 官方区分默认 Basic 编辑器与可选择的 VS Code 环境。官方为 VS Code 环境说明了 IntelliSense、调试器与终端支持。不能把 Codility 概括为“全部没有补全”，也不能假设某场考试一定有这些工具。

| 环境 | 准备策略 |
| --- | --- |
| Basic / 单文件编辑器 | 按不依赖 C++ 智能补全准备，熟悉 STL 接口，频繁编译 |
| 配置好的 VS Code 环境 | 使用实际提供的语言工具、终端和调试能力 |
| 本地 IDE 被明确允许 | 使用熟悉配置，但不依赖面试环境未提供的扩展 |

AI 补全与普通语义补全是不同能力，允许范围分别按面试说明处理。

### 8.2 本地调试编译

仅在能控制编译命令、环境支持时使用：

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -O1 \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    main.cpp -o app
```

ASan / UBSan 能帮助发现部分内存错误和未定义行为，不能证明程序正确，也不能代替语义测试。不要把 sanitizer 构建的运行表现当作最终性能表现。

### 8.3 最少的命令行与 GDB 操作

```bash
./app < input.txt > actual.txt
diff -u expected.txt actual.txt
```

GDB 练熟：设置断点、条件断点、单步、打印变量、调用栈。例如只在某个 step 或 ID 时停止。命令中的变量和文件位置要替换为当前程序的真实对象。

仅在 GNU libstdc++ 环境且能控制构建时，可考虑本地使用 `-D_GLIBCXX_DEBUG` 辅助检查部分容器与迭代器误用；它会影响类型、性能和兼容性，不是通用平台选项。

## 9. 两小时安排与慌乱时的恢复

下面是训练预算，不是固定评分标准。题面长度、熟悉程度和额外要求不同，应调整。

| 时间 | 检查点 |
| --- | --- |
| 0–20 分钟 | 需求表、整体路线、关键手算例子 |
| 20–30 分钟 | 数据结构、阶段骨架、核心接口 |
| 30–85 分钟 | 完成必需路径，包括全局失败条件；持续编译验证 |
| 85–110 分钟 | 针对性测试、修复、必要的复杂度检查；余力再做 Bonus |
| 110–120 分钟 | 最新版本编译运行、输出格式、关闭调试、提交检查 |

读题期间没有代码，也可能是在消除昂贵的返工风险。与此同时，不必等到完全放心：路线能复述、关键反例能解释，就应开始实现。

时间紧张时，优先完成和验证必需功能。是否保留较慢基线或部分功能，应根据约束和实际评分信息决定，不能假定平台一定给某种部分分。

### 一两分钟恢复动作

暂停同时推进多个问题，写下：

1. 已经可靠完成什么？
2. 还缺哪些必需功能？
3. 下一步最小、可验证的动作是什么？

Headlands 示例：已完成解析和归并；尚缺冲突检查、索引、查询；下一步按最终 root 检查冲突，并用一个传递冲突例子验证。

完成这一个动作后，再选择下一步。避免同时重写 parser、优化容器和补查询。

## 10. 练习顺序与复盘指标

### 10.1 建议顺序

1. 输入处理专项：数字、字段、空行、EOF、正常与异常路径。
2. 棋盘专项：打印状态、坐标、碰撞、删除与压缩。
3. 完整方块模拟：按明确规则限时实现，不默认需要 GUI。
4. 重做 Headlands：先写需求表，再按阶段完成；记录是否还有迟发现的核心要求。
5. 二选一完整任务：简化订单簿或分片输入的 binary decoder。
6. 一次读代码修复 / 优化练习，训练从陌生实现入手。

时间有限时，优先做少量有复盘的完整练习，专项用于修复已经暴露的薄弱点。标准 LRU / LFU 和 queue 保持基础能力，不作为当前长题训练的主要投入。

### 10.2 每次记录

| 指标 | 要观察的问题 |
| --- | --- |
| 首次完成整体设计的时间 | 是否在模型未闭合时就开始编码 |
| 首次编译成功的时间 | 是否累计太多未经编译的代码 |
| 首次跑通完整正常案例的时间 | 是否长期只完成孤立模块 |
| 中途才发现的核心需求数量 | 读题清单是否有效 |
| 首次覆盖全局失败路径的时间 | 是否把必要错误路径推到最后 |
| bug 类型与修复耗时 | 语义、边界、状态、生命周期、复杂度、格式分别占多少 |
| 预留验证时间 | 是否只在最后几分钟测试 |

只记录做了多少行代码或是否最终完成，不足以定位流程问题。重做熟悉题主要验证流程改善；陌生题才能进一步检验迁移能力。
