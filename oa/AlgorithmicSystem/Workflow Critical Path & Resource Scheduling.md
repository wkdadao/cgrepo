# C3.4 — Workflow Critical Path & Resource Scheduling（关键路径与资源受限调度）

> **C3 / Algorithmic System / Workflow Critical Path & Resource Scheduling**  
> 建议用时：**90–120 分钟** ｜ 语言：**C++17/20** ｜ 难度：**中高至高**  
> 训练重点：DAG 建模、关键路径、依赖约束、确定性资源调度、事件时间推进、动态更新  
> **本文件仅包含完整题目描述、样例和测试要求；不包含算法提示或参考实现。**

## 1. Problem Statement

某交易基础设施团队需要运行一批相互依赖的任务，例如：准备行情数据、生成风险参数、构建报价、汇总结果。

每个任务有固定的执行时长，有些任务必须在其他任务完成后才能开始。系统提供有限数量的相同 Worker，每个 Worker 同一时刻最多只能执行一个任务，每个任务也只能由一个 Worker 执行。

系统需要支持两类查询：

- **CRITICAL**：求当前依赖图中的关键路径长度，并输出一条满足指定规则的关键路径。
- **PLAN W**：给定 `W` 个 Worker，按照本题定义的**确定性贪心规则**生成完整调度，输出总完成时间（Makespan）以及每个任务的开始、结束时间。

用户还可以修改任务时长，增加或删除依赖关系。所有查询均针对修改后的**当前工作流**。

**重要**：`PLAN` 只要求遵循规定的调度优先级，**不要求找到所有可能调度中的最短 Makespan**。不要将“调度策略正确”与“全局最优调度”混为一谈。

## 2. Task & Dependency Model

有 `N` 个任务，ID 固定为 `0` 至 `N-1`。

每个任务 `u` 拥有：

- `duration[u]`：正整数执行时长；
- 一组前置任务 `predecessors[u]`；
- 一组直接后继任务 `successors[u]`。

依赖 `u -> v` 的含义是：**任务 `u` 必须执行完成后，任务 `v` 才能开始**。

约束：

1. 整个依赖图始终是**有向无环图（DAG）**。
2. 同一个有向依赖 `u -> v` 最多出现一次。
3. 依赖有方向；`u -> v` 不等于 `v -> u`。
4. 不存在自依赖 `u -> u`。
5. **任务不可抢占**：开始后连续执行 `duration[u]` 个时间单位，直到完成。
6. 每个任务在一次 `PLAN` 中**恰好执行一次**。
7. 所有 Worker 相同，不考虑任务切换成本或通信延迟。
8. Worker 可以空闲；任务一旦就绪并按优先级被选中，若有空闲 Worker，则必须立即开始。
9. `CRITICAL` 和 `PLAN` 都是**只读查询**，不会修改工作流。
10. 一次查询的调度完成后，下次 `PLAN` 从时间 0 开始重新模拟，不延续上次的运行状态。

## 3. CRITICAL — Critical Path

一条**依赖路径**是任务序列

~~~text
v_1 -> v_2 -> ... -> v_k
~~~

其中每对相邻任务都有直接依赖。单独一个任务也算长度为 1 个节点的路径。

路径的**总时长**定义为：

~~~text
duration[v_1] + duration[v_2] + ... + duration[v_k]
~~~

**关键路径长度**是所有依赖路径中总时长的最大值。

由于所有任务执行时长都严格为正，关键路径是无限 Worker 情况下所有任务完成所需时间的一个下界。本题中无限 Worker 指至少 `N` 个 Worker。

### 3.1 多条关键路径时如何选择

如果有多条路径具有相同的最大总时长，选取**任务 ID 序列字典序最小**的一条。

字典序使用任务 ID 的**整数大小**进行比较，逐项比较第一个不同的 ID；如果一个序列是另一个序列的前缀，较短者更小。

例如：

~~~text
0 -> 3 -> 5
1 -> 2 -> 5
~~~

若两条路径总时长相等，选择 `0 3 5`。

**输出格式（一行）：**

~~~text
criticalDuration K id_1 id_2 ... id_K
~~~

其中：

- `criticalDuration` 是最大路径总时长；
- `K` 是选定路径包含的**任务数量**；
- 后续 `K` 个整数是路径的任务 ID，按执行依赖顺序排列。

## 4. PLAN W — Deterministic Resource Scheduling

给定 `W` 个 Worker，要求生成满足所有依赖关系的调度。

每个任务恰好运行一次，必须等全部前置任务完成，且有空闲 Worker 才能开始。

### 4.1 Remaining Critical Length

在执行 `PLAN` 前，针对**当前依赖图与时长**，为每个任务 `u` 定义：

> `remainingCritical[u]` = 从任务 `u` 开始，沿依赖边向后走的所有路径中，最大的任务时长总和（**包含任务 u 自身的 duration**）。

例如，任务 `u` 后面没有任何直接后继时：

~~~text
remainingCritical[u] = duration[u]
~~~

该优先级在本次 `PLAN` 中保持不变。它由工作流自身定义，**不**随着模拟过程中已完成任务的数量动态改变。

### 4.2 Ready 的定义

任务 `u` 进入 Ready 集合，当且仅当：

- 它尚未开始运行；
- **所有直接前置任务都已完成**。

没有任何前置任务的任务在 `t = 0` 就绪。

### 4.3 任务选择优先级

当有空闲 Worker 和多个 Ready 任务时，按照以下严格优先级选任务：

1. `remainingCritical` **较大**者优先；
2. 若该值相同，**任务 ID 较小**者优先。

依次启动最高优先级 Ready 任务，直到没有空闲 Worker 或没有 Ready 任务。

**不允许主动让 Worker 空闲来等待某个尚未 Ready 的高优先级任务。**

### 4.4 时间推进与同一时刻的事件

调度从整数时间 `t = 0` 开始。

- 启动任务 `u` 的时间为 `start[u] = t`。
- 结束时间为 `finish[u] = t + duration[u]`。
- 一个任务占用 Worker 的半开区间为 `[start[u], finish[u])`。
- 在任务运行过程中，不允许中断、暂停或迁移。
- 如果当前 Ready 集合为空，且还有任务运行，时间直接推进到**最早的任务完成时刻**。

**同一时间戳上的事件顺序非常重要。**

当时间推进到 `t` 时：

1. **首先统一处理全部在 `t` 完成的任务**；
2. 释放这些任务占用的全部 Worker；
3. 根据全部已完成任务更新依赖关系，将新满足条件的任务加入 Ready；
4. 再根据第 4.3 节的优先级，利用全部空闲 Worker 启动任务；
5. 重复时间推进，直到所有任务都已完成。

例如，在 `t = 5` 同时完成两个任务，而第三个任务依赖二者时，第三个任务可以**恰好在 `t = 5` 启动**。

所有任务时长为正整数，因此不会出现某个新启动任务也在同一时间戳结束的情况。

### 4.5 PLAN 输出

输出恰好 `N + 1` 行：

第一行：

~~~text
makespan
~~~

其中 `makespan = max(finish[u])`，即所有任务完成的最晚时间。

随后按**任务 ID 从小到大**，对每个任务输出一行：

~~~text
id start finish
~~~

说明：

- 不需要输出 Worker ID；Worker 在本题中是同质的。
- `start` 和 `finish` 都是整数时间。
- 输出顺序是**任务 ID 升序**，不是启动时间或完成时间的先后顺序。
- 不在 `PLAN` 结果间插入空行或标签。

## 5. Commands

所有命令按照输入顺序生效，命令名大写。

### 5.1 `SET_DURATION u newDuration`

将任务 `u` 的执行时长改为 `newDuration`。

- `newDuration` 保证是有效正整数；
- 修改立即影响后续 `CRITICAL` 和 `PLAN`；
- 无输出。

### 5.2 `ADD_DEP u v`

新增依赖 `u -> v`。

输入保证：

- `u != v`；
- 该依赖当前不存在；
- **新增后依赖图仍为 DAG**；
- 活跃依赖总数不超过规定上限。

无输出。

### 5.3 `REMOVE_DEP u v`

删除当前存在的依赖 `u -> v`。

输入保证该依赖存在。

无输出。

### 5.4 `CRITICAL`

按照第 3 节的规则，输出当前关键路径的总时长与选定路径的任务 ID。

输出一行。

### 5.5 `PLAN W`

按照第 4 节生成完整调度。

输出 `N + 1` 行。

## 6. Input Format

~~~text
N M
duration_0 duration_1 ... duration_(N-1)
u_1 v_1
...
u_M v_M
Q
command_1
...
command_Q
~~~

其中：

- `N`：固定任务数量；
- `M`：初始依赖数量；
- 第二行依次给出任务 `0` 至 `N-1` 的执行时长；
- 接下来 `M` 行，每行描述一条依赖 `u -> v`；
- 然后一行 `Q`；
- 最后 `Q` 行，每行一条命令。

数据以空白字符分隔。初始依赖组成一个 DAG。

## 7. Constraints

| 项目 | 约束 |
| --- | --- |
| 任务数量 | `1 <= N <= 60` |
| 初始依赖数量 | `0 <= M <= 300` |
| 任意时刻活跃依赖数量 | `<= 300` |
| 任务 ID | `0 <= u, v < N` |
| 任务时长 | `1 <= duration, newDuration <= 1,000,000` |
| Worker 数量 | `1 <= W <= N` |
| 命令数量 | `1 <= Q <= 200` |

附加保证：

- 初始依赖没有重复，且满足 DAG 条件；
- 任意 `ADD_DEP` 后仍然是 DAG，不需要处理环或输出 `ERROR`；
- `REMOVE_DEP` 总是删除当前已存在的依赖；
- 所有任务永远保留，不存在任务新增或删除；
- 输入格式和所有参数均合法。

建议使用 64 位整数存储时间和累计路径长度。

## 8. Samples

### Sample 1 — 基本关键路径与不同 Worker 数量

**Input**

~~~text
5 4
4 3 2 5 1
0 2
1 2
2 3
2 4
3
CRITICAL
PLAN 2
PLAN 1
~~~

**Output**

~~~text
11 3 0 2 3
11
0 0 4
1 0 3
2 4 6
3 6 11
4 6 7
15
0 0 4
1 4 7
2 7 9
3 9 14
4 14 15
~~~

**Explanation**

- `0 -> 2 -> 3` 的总时长为 `4 + 2 + 5 = 11`，是关键路径。
- 两个 Worker 时，任务 0、1 并行；任务 2 等二者都完成才能在 `t = 4` 开始，任务 3 与 4 在 `t = 6` 并行运行，Makespan 为 11。
- 一个 Worker 时，所有任务都串行执行，Makespan 为全部任务时长之和 15。

### Sample 2 — 优先级取决于后续路径，而非单个任务时长

**Input**

~~~text
5 3
4 4 2 4 1
0 2
1 3
2 4
5
CRITICAL
PLAN 1
SET_DURATION 0 7
CRITICAL
PLAN 2
~~~

**Output**

~~~text
8 2 1 3
15
0 4 8
1 0 4
2 12 14
3 8 12
4 14 15
10 3 0 2 4
10
0 0 7
1 0 4
2 7 9
3 4 8
4 9 10
~~~

**Explanation**

- 初始时，任务 1 的 `remainingCritical` 为 8，任务 0 为 7，因此只有一个 Worker 时，任务 1 **先于**任务 0 开始，尽管 ID 1 更大。
- 更新任务 0 的时长后，`0 -> 2 -> 4` 成为新的关键路径，总时长 10。
- 两个 Worker 时，任务 0 与 1 可以在时间 0 同时运行。

### Sample 3 — 动态删除和新增依赖

**Input**

~~~text
4 3
3 2 5 4
0 2
1 2
2 3
7
CRITICAL
PLAN 2
REMOVE_DEP 0 2
CRITICAL
PLAN 1
ADD_DEP 0 3
PLAN 2
~~~

**Output**

~~~text
12 3 0 2 3
12
0 0 3
1 0 2
2 3 8
3 8 12
11 3 1 2 3
14
0 11 14
1 0 2
2 2 7
3 7 11
11
0 0 3
1 0 2
2 2 7
3 7 11
~~~

**Explanation**

- 初始关键路径是 `0 -> 2 -> 3`，总时长为 12。
- 删除 `0 -> 2` 后，关键路径改为 `1 -> 2 -> 3`，总时长 11。
- 此时只有一个 Worker 时，确定性调度会先执行任务 1、2、3，再执行独立任务 0，总完成时间为 14。
- 新增 `0 -> 3` 后，两个 Worker 的调度需要同时满足任务 3 的两项前置条件。

### Sample 4 — 没有依赖，关键路径并列

**Input**

~~~text
4 0
2 2 2 2
3
CRITICAL
PLAN 2
PLAN 4
~~~

**Output**

~~~text
2 1 0
4
0 0 2
1 0 2
2 2 4
3 2 4
2
0 0 2
1 0 2
2 0 2
3 0 2
~~~

**Explanation**

- 四个单任务路径长度都是 2，字典序最小的是 `[0]`。
- 两个 Worker 时，先运行任务 0、1，再运行 2、3。
- 四个 Worker 时，所有任务在时间 0 开始，时间 2 完成。

### Sample 5 — 同时完成、批量解锁与 Ready 优先级

**Input**

~~~text
6 5
4 2 4 1 3 2
0 3
1 3
2 4
3 5
4 5
2
CRITICAL
PLAN 2
~~~

**Output**

~~~text
9 3 2 4 5
9
0 0 4
1 4 6
2 0 4
3 6 7
4 4 7
5 7 9
~~~

**Explanation**

- 任务 2 的 `remainingCritical = 4 + 3 + 2 = 9`，优先级高于任务 0 的 7，因此在时间 0 先选 2，再选 0。
- 时间 4，任务 0 和 2 **同时完成**；任务 4 新进入 Ready。此时任务 1 和任务 4 的 `remainingCritical` 都是 5。
- 因为 ID 1 小于 4，所以时间 4 启动任务 1 和任务 4，分别在时间 6 与 7 结束。
- 时间 6，任务 1 完成，使任务 3 Ready；任务 3 在时间 6 开始。
- 时间 7，任务 3 和 4 均已完成，任务 5 才能启动。

## 9. Additional Testing Requirements

提交前请至少自行构造以下测试：

1. `N = 1`，没有依赖，`CRITICAL` 与 `PLAN 1`。
2. 完全没有依赖的多个任务，所有时长不同。
3. 所有任务形成一条链。
4. 多个起点汇聚到同一个后继任务（Fan-in）。
5. 一个任务解锁多个后继任务（Fan-out）。
6. 多条不同的关键路径具有相同总时长，验证**整数 ID 字典序**的选择规则（包括 ID ≥ 10 的情况）。
7. `remainingCritical` 相同但单个任务时长不同，验证优先级只使用定义好的两级规则。
8. 若有 Ready 任务且 Worker 空闲，不能故意延迟运行。
9. 多个任务在同一时刻完成，并共同解锁后续任务。
10. `SET_DURATION` 修改后，关键路径和调度优先级同时发生改变。
11. `ADD_DEP`、`REMOVE_DEP` 交替执行，后续查询使用当前图。
12. `PLAN 1` 与 `PLAN N`，比较 Makespan 和执行区间。
13. 连续执行多次 `PLAN`，验证调度不会保留上次的运行状态。
14. 时间与累计路径较大时，验证整数类型不会溢出。
15. 检查每个任务只运行一次、任务区间长度等于 `duration`、并发运行数量不超过 `W`。

## 11. OA Self-Review Checklist

- [ ] 所有依赖均按有向边 `u -> v` 处理。
- [ ] 关键路径长度是**任务时长总和**，不是边数或任务数。
- [ ] `CRITICAL` 在多解时按整数序列字典序打破平局。
- [ ] `remainingCritical` 包含任务自身，并在每次查询时基于当前图和时长计算。
- [ ] `PLAN` 按 `remainingCritical` 降序、任务 ID 升序选任务。
- [ ] 同时刻先批量完成全部任务，再统一更新 Ready 并启动任务。
- [ ] 没有 Worker 在 Ready 任务存在时无故空闲。
- [ ] 每个任务恰好执行一次且不会在前置任务完成前开始。
- [ ] 运行区间满足 `finish - start == duration`，Makespan 等于最大的结束时间。
- [ ] 输出任务按照 **ID 升序**，而不是按完成时间排序。
- [ ] 所有更新只影响后续查询，`CRITICAL` 和 `PLAN` 不改变工作流。
- [ ] 实际编译、运行五组样例及自行设计的边界案例。
