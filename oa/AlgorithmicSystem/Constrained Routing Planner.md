# C3.1 — Constrained Routing Planner（多约束动态路由规划）

> **C3 / Algorithmic System / Constrained Routing Planner**  
> 建议用时：**90–120 分钟** ｜ 语言：**C++17/20** ｜ 难度：**中高**  
> 训练重点：从业务约束中抽象算法问题、动态有向图、多条件最优解、复杂度分析、边界测试  
> **本文仅提供完整题面、样例、测试要求；不包含算法提示、参考解法或代码。**

## 1. Problem Statement

某电子交易系统通过多个 Market Gateway 转发行情与交易消息。Gateway 之间由若干**有向通信链路**连接。每条链路都有通信延迟（latency）和费用（fee）。

系统需要不断处理链路新增、修改、删除，以及最优路由查询。对于一条查询，必须在**跳数限制**和**费用预算**之内找到最优路线。

你的任务是实现一个单线程的命令行程序，按照输入顺序处理所有命令，并为每条 `QUERY` 输出结果。

本题关注算法正确性和完整的程序实现，而非真实网络传输、并发或交易协议。

## 2. Graph Model

共有 `N` 个 Gateway，编号为 `0` 到 `N-1`。网络是一个**有向多重图**。

每条当前存在的链路有以下属性：

| 字段 | 含义 |
| --- | --- |
| `id` | 链路的唯一整数 ID |
| `u` | 起点 Gateway |
| `v` | 终点 Gateway |
| `latency` | 正整数延迟 |
| `fee` | 非负整数费用 |

明确规则：

- 链路 `u -> v` **不能**反向使用，除非另外存在 `v -> u`。
- 可以有**平行边**：相同 `u`、`v` 的多条链路可以拥有不同 `id` 和不同属性。
- 允许 `u == v` 的**自环边**。
- 任意时刻，活跃链路的 `id` 必须唯一；删除链路后，允许重新使用该 `id`。
- 初始链路 ID 互不相同。
- `UPDATE` 仅修改延迟与费用，不修改链路的两个端点。
- 费用与延迟始终按照**实际经过的每条边**分别累加。

一个路线（walk）由零条或多条方向相连的链路组成，**允许重复经过节点和边**。

对于一条路线，定义：

~~~text
totalLatency = sum(latency of traversed edges)
totalFee     = sum(fee of traversed edges)
hopCount     = number of traversed edges
~~~

`hopCount` 是边的数量，而不是访问过的不同节点数量。

## 3. Routing Query

查询格式：

~~~text
QUERY s t maxHops budget
~~~

路线必须同时满足：

1. 起点是 `s`，终点是 `t`。
2. `hopCount <= maxHops`。
3. `totalFee <= budget`。

在**全部合法路线**中，按照以下严格优先级选择最优路线：

1. **总延迟更小**者优先；
2. 总延迟相等时，**总费用更小**者优先；
3. 总延迟与总费用都相等时，**跳数更少**者优先。

即按照三元组

~~~text
(totalLatency, totalFee, hopCount)
~~~

进行**字典序升序**比较。

若三项都相同，任意一条并列路线都合法。**不要求输出具体节点序列或链路 ID。**

特殊情况：

- `s == t` 时，**零跳路线**始终合法：延迟、费用、跳数均为 0。因此结果为 `0 0 0`。
- `maxHops == 0` 时，只能使用零跳路线。
- 预算可以正好用完（`totalFee == budget` 合法）。
- 允许费用为 0 的链路，但所有链路延迟都是正整数。
- 若不存在合法路线，输出 `IMPOSSIBLE`。

## 4. Commands

输入中包含以下四类命令，按出现顺序立即生效。

### 4.1 `ADD id u v latency fee`

新增一条从 `u` 到 `v` 的有向链路。

### 4.2 `UPDATE id latency fee`

更新**当前存在**的链路 `id` 的延迟和费用；保留原起点、终点。

### 4.3 `REMOVE id`

删除当前存在的链路 `id`。

### 4.4 `QUERY s t maxHops budget`

在**当前网络状态**下执行路由查询，并输出一行结果。

**输入保证：**

- `ADD` 的 `id` 在该命令执行前不属于任何活跃链路；
- `UPDATE` 和 `REMOVE` 指向当前存在的链路；
- 所有命令参数都在规定范围内。

因此**不需要处理非法命令或输出 `ERROR`**。

**只有 `QUERY` 产生输出。** `ADD`、`UPDATE` 和 `REMOVE` 均不输出任何内容。

## 5. Input Format

~~~text
N M
id_1 u_1 v_1 latency_1 fee_1
...
id_M u_M v_M latency_M fee_M
Q
command_1
...
command_Q
~~~

- 第一行 `N M`：Gateway 数量、初始链路数量。
- 接下来 `M` 行：每行五个整数，描述一条初始链路。
- 随后一行 `Q`：需要处理的命令数量。
- 接下来恰好 `Q` 行：每行一条命令，格式参照第 4 节。

所有字段用一个或多个空白字符分隔，命令名使用大写英文。

## 6. Output Format

对于每条 `QUERY`，输出**恰好一行**：

- 有合法路线：`totalLatency totalFee hopCount`；
- 没有合法路线：`IMPOSSIBLE`。

不要打印提示文字、调试信息或命令处理成功标记。

## 7. Constraints

| 项目 | 约束 |
| --- | --- |
| Gateway 数量 | `1 <= N <= 60` |
| 初始链路数量 | `0 <= M <= 300` |
| 整份输入出现的**不同链路 ID** 数量 | 不超过 `300` |
| 链路 ID | `1 <= id <= 10^9` |
| 节点编号 | `0 <= u, v, s, t < N` |
| 链路延迟 | `1 <= latency <= 1,000,000` |
| 链路费用 | `0 <= fee <= 100` |
| 命令数量 | `1 <= Q <= 200` |
| 查询跳数限制 | `0 <= maxHops <= 12` |
| 查询费用预算 | `0 <= budget <= 100` |

由于链路 ID 的种类总数不超过 300，任意时刻的活跃链路数量也不会超过 300。

为避免中间计算溢出，建议延迟累计使用 64 位整数。

## 8. Samples

### Sample 1 — 动态更新与删除

**Input**

~~~text
3 3
1 0 1 5 2
2 1 2 5 2
3 0 2 13 0
6
QUERY 0 2 2 4
QUERY 0 2 1 4
UPDATE 3 8 5
QUERY 0 2 2 4
REMOVE 2
QUERY 0 2 2 4
~~~

**Output**

~~~text
10 4 2
13 0 1
10 4 2
IMPOSSIBLE
~~~

**Explanation**

- 第 1 次查询：`0 -> 1 -> 2`，总延迟 10、费用 4、跳数 2，优于直达边。
- 第 2 次查询：最多 1 跳，只能选直达边。
- 修改直达边后，它的费用为 5，超过预算 4；第 3 次仍选两跳路线。
- 删除 `1 -> 2` 后，预算内已无法到达终点。

### Sample 2 — 先比较费用，再比较跳数

**Input**

~~~text
4 5
1 0 1 4 3
2 1 3 6 2
3 0 2 4 1
4 2 3 6 3
5 0 3 10 5
4
QUERY 0 3 2 10
UPDATE 4 6 4
QUERY 0 3 2 10
QUERY 0 3 2 4
~~~

**Output**

~~~text
10 4 2
10 5 1
IMPOSSIBLE
~~~

**Explanation**

- 初次查询时，三条候选路线的延迟均为 10；经 `2` 的路线费用 4，为最优。
- 更新链路 `4` 后，两条两跳路线费用都是 5，与直达路线相同；直达路线只需要 1 跳，因此胜出。
- 费用预算降到 4 后，三条路线均不合法。

### Sample 3 — 零跳、自环语义与方向性

**Input**

~~~text
3 3
1 0 1 3 0
2 1 0 2 0
3 1 2 4 1
4
QUERY 0 0 0 0
QUERY 0 2 2 1
QUERY 0 2 1 1
QUERY 1 0 3 0
~~~

**Output**

~~~text
0 0 0
7 1 2
IMPOSSIBLE
2 0 1
~~~

### Sample 4 — 预算与跳数都是硬约束

**Input**

~~~text
3 3
1 0 1 1 100
2 1 2 1 0
3 0 2 5 0
4
QUERY 0 2 2 99
QUERY 0 2 2 100
QUERY 0 2 1 100
QUERY 0 2 0 100
~~~

**Output**

~~~text
5 0 1
2 100 2
5 0 1
IMPOSSIBLE
~~~

**Explanation**

延迟最低的两跳路线总费用恰好为 100。它在预算 100 时合法，在预算 99 时不合法；同时也受跳数上限影响。

### Sample 5 — 平行边与删除后重用 ID

**Input**

~~~text
2 2
1 0 1 5 2
2 0 1 5 1
7
QUERY 0 1 1 2
REMOVE 2
QUERY 0 1 1 2
ADD 2 0 1 3 2
QUERY 0 1 1 2
UPDATE 2 7 0
QUERY 0 1 1 2
~~~

**Output**

~~~text
5 1 1
5 2 1
3 2 1
5 2 1
~~~

### Sample 6 — 预算边界与不可达

**Input**

~~~text
4 4
1 0 1 2 2
2 1 3 2 3
3 0 2 3 0
4 2 3 3 0
4
QUERY 0 3 2 4
QUERY 0 3 2 5
QUERY 0 3 1 5
QUERY 3 0 2 100
~~~

**Output**

~~~text
6 0 2
4 5 2
IMPOSSIBLE
IMPOSSIBLE
~~~

## 9. Additional Testing Requirements

提交前请自行设计并运行额外测试，至少覆盖：

1. `N = 1`，没有边，`QUERY 0 0 0 0`。
2. 初始没有边，随后 `ADD` 才使路线可达。
3. 两个节点之间有多条平行边，其中一条被 `REMOVE`。
4. `UPDATE` 后最优路径发生变化；其他查询仍使用**最新状态**。
5. 延迟相同、费用不同；延迟和费用均相同、跳数不同。
6. 费用**恰好**达到预算上限；超出预算 1 则不合法。
7. 跳数**恰好**达到上限；超出上限 1 则不合法。
8. 存在环或自环，但路线不得突破跳数上限。
9. `s != t` 且 `maxHops = 0`。
10. 只有单向边，反向查询不可达。
11. 费用为 0 的多跳路径。
12. 多次查询穿插更新、删除与重新添加同一 ID。

注意：不要只验证样例；样例并不覆盖所有状态组合。
