# 多线程题目

> 自拟 C++17 接口练习题集，并非已核实的 DRW 或其他公司的原题。以下接口、异常与并发行为均为练习约定；每题独立完成，不要求一次实现全部组件。本文只包含题目描述和行为示例，不提供实现或解题提示。

## 练习列表

| 建议顺序 | 题目 | 核心要求 |
| --- | --- | --- |
| 1 | 写者优先读写锁 | 多读者并行、写者独占、准入与唤醒 |
| 2 | 同键加载去重缓存 | 合并并发加载、异常共享、覆盖与失效 |
| 3 | 按 key 保序的任务执行器 | 同键串行、异键并行、背压与关闭 |
| 4 | 并发定时任务调度器 | 添加、取消、重新调度、停止 |
| 5 | 并行处理与保序输出 | 乱序完成、顺序取结果、在途数量上限 |

该顺序是准备建议，不表示实际面试中的出现概率。

## 共同约定

- 采用接口调用形式，由测试程序从真实线程调用，不规定标准输入、标准输出协议。
- 组件均不可复制、不可移动。构造完成后，才会被其他线程使用。
- 析构开始时，不再有其他外部接口调用正在进行，也不会发起新调用。组件自己的内部线程由组件负责回收。
- 所有可运行线程持续获得执行机会；用户回调最终返回或抛出异常，不回调所属组件，也不存在用户回调之间的循环等待。
- 等待型操作不得依靠持续轮询维持等待。
- 运行环境提供足够内存与系统线程资源。
- 以下出现的 key 均为长度 1～16 的 ASCII 字母、数字或下划线字符串，区分大小写。非法 key 抛出 `std::invalid_argument`。
- 要求为正的容量、线程数若为 0，或传入空的函数对象，均抛出 `std::invalid_argument`。参数校验先于命中判断和关闭状态判断。
- 因关闭而拒绝新工作的接口，统一抛出 `ComponentClosed`。该异常公开继承 `std::runtime_error`，错误文本不限。
- 除单独说明外，不要求等待线程之间的 FIFO 公平性。行为示例明确规定的先后关系由测试程序协调；其他线程交错不作为判定条件。

## 题目一：写者优先读写锁

### 题目描述与接口

实现非递归读写锁 `WriterPreferredRWLock`，提供：

```text
void lock_shared();
void unlock_shared();
void lock();
void unlock();
```

需要自行实现共享、独占及准入规则，不能直接包装现成的读写锁。

### 行为规则

1. 没有写者持锁、也没有写者等待时，允许多个读者同时持锁。
2. 写者持锁期间，其他读者和写者均不能进入。
3. 写者需要等所有现有读者退出，以及前一个写者退出后，才能取得锁。
4. 一旦有写者进入等待状态，之后到来的读者不得抢在等待写者之前进入。
5. 已持锁读者可以继续执行并正常退出，不被强制中断。
6. 多个写者之间不要求 FIFO。
7. 不支持递归、读锁直接升级为写锁或写锁直接降级为读锁。调用方只会释放自己已取得的对应锁。
8. 锁的获取与释放须提供受保护数据所需的同步和可见性。
9. 析构前，调用方保证没有持锁者或等待者。

本题规定写者优先。持续到来的写者可能延迟读者，本题不额外要求读写双方都无饥饿。

### 行为示例

| 步骤 | 操作 | 必须满足的结果 |
| --- | --- | --- |
| 1 | R1、R2 分别取得读锁，并保持持锁 | 两者可以同时进入 |
| 2 | W 请求写锁，进入等待 | W 尚不能进入 |
| 3 | 在 W 已等待后，R3 请求读锁 | R3 必须等待 |
| 4 | R1 释放读锁，R2 仍持锁 | W、R3 均不能进入 |
| 5 | R2 释放读锁 | W 必须能先于 R3 取得锁 |
| 6 | W 释放写锁，且没有其他等待写者 | R3 必须能继续取得读锁 |

还会测试：多个等待写者、最后一个读者退出、无竞争的重复加解锁，以及受保护数据的并发读取和更新。

## 题目二：同键加载去重缓存

### 题目描述与接口

实现 `SingleFlightCache`，键为字符串，值为 `std::int64_t`：

```text
using Loader = std::function<std::int64_t()>;

std::int64_t getOrLoad(const std::string& key, Loader loader);
void put(const std::string& key, std::int64_t value);
void erase(const std::string& key);
```

初始缓存为空。本题不设置容量淘汰或 TTL，集中规定并发加载和覆盖行为。

### 命中与加载

1. 缓存中已有值时，`getOrLoad` 返回该值，不执行传入的 loader。
2. 键不存在且没有该键的加载进行中时，发起一次加载。
3. 键不存在但已有该键的加载进行中时，加入该次加载，调用方自己传入的 loader 不执行。
4. 同一个键，同一时刻最多执行一个 loader。不同键的 loader 必须能够并发执行。
5. 每次加载及加入它的调用构成一个“加载批次”。加入批次后，调用的结果固定属于该批次。
6. loader 成功返回时，该批次所有调用取得相同结果；未被后续修改失效的加载结果存入缓存。
7. loader 抛出异常时，该批次所有调用重新抛出相同类型及可观察信息的异常。失败结果不缓存；之后仍缺失的请求可以发起新加载。

### 加载期间的修改

- `put` 立即设置当前缓存值；`erase` 立即移除当前缓存值。删除不存在的键是合法操作。
- 两者都不取消正在进行的同键加载，也不等待 loader 完成。
- 加载期间发生过该键的 `put` 或 `erase` 后，该次旧加载完成时不得再回写缓存。
- 已加入旧批次的调用仍取得该批次的结果或异常，不改为返回 `put` 的值。
- 新请求先判断当前是否有缓存值：有值则返回当前值；无值而旧批次尚在进行，则仍加入旧批次。
- 旧批次结束后，若该键仍无缓存值，下一次请求可以发起新加载。
- 一个键的 loader 正在等待时，其他键的请求，以及 `put`、`erase`，仍须能够继续执行。

### 行为示例

**场景 A：并发加载合并。**

多个线程请求缺失键 A，最先发起的 loader 最终返回 7。其余调用在加载完成前加入同一批次。

结果：只执行一次 loader；该批次所有调用都返回 7。随后对 A 的请求直接命中 7。

**场景 B：旧加载不得覆盖新值。**

A 的旧 loader 正在执行，随后 `put(A, 9)` 完成；旧 loader 最终返回 7。

结果：旧批次调用返回 7；旧加载不得覆盖 9；此后的缓存命中返回 9。

**场景 C：删除使旧加载不能回写。**

A 的 loader 正在执行，随后 `erase(A)` 完成；loader 最终返回 7。

结果：旧批次仍返回 7，但缓存中不重新存入 7；旧批次结束后的下一次缺失请求重新加载。

## 题目三：按 key 保序的任务执行器

### 题目描述与接口

实现 `KeyedTaskExecutor`：

```text
using Task = std::function<std::int64_t()>;

KeyedTaskExecutor(std::size_t workerCount, std::size_t capacity);
std::future<std::int64_t> submit(const std::string& key, Task task);
void shutdown();
~KeyedTaskExecutor();
```

`workerCount` 与 `capacity` 均必须大于 0。

### 顺序与并行规则

1. 每个成功接受的任务恰好执行一次，结果或异常交给其独立的 future。
2. 同一 key 的任务，按成功接受顺序串行执行。前一任务结束并记录结果或异常后，下一任务才可开始。
3. 不同 key 的任务可以并行，不规定跨 key 的全局执行顺序。
4. 并发重叠提交的接受顺序可以任意确定；前一提交已成功返回、后一提交才开始时，必须保持该先后关系。
5. 一个 key 的前序任务尚未结束时，不能因此阻止可独立执行的其他 key 任务使用剩余工作线程。
6. 某个任务抛出异常，不得阻止同 key 的后续任务或其他 key 的任务继续执行。

### 容量与关闭

- 容量限制所有已接受但尚未开始执行的任务总数，不含运行中的任务。
- 队列满时，`submit` 等待空位或关闭。任务成功加入待执行集合时视为被接受。
- 关闭后尚未接受的任务被拒绝并抛出 `ComponentClosed`；等待提交者必须能结束等待。
- `shutdown` 停止接受任务，执行完所有已接受任务，并回收全部工作线程后返回。
- 允许并发或重复调用 `shutdown`；每个调用返回时，所有已接受任务均已结束。
- 析构具有完成一次 `shutdown` 的效果。
- 用户任务由固定工作线程执行，不得每次提交另建线程。

### 行为示例

工作线程数为 2，等待容量为 2：

1. 接受并开始执行 A1，key 为 A；A1 等待测试程序允许其继续。
2. 接受 A2，key 同为 A。
3. 接受 B1，key 为 B。
4. A1 尚未结束时，A2 不得开始，但 B1 必须能够执行并完成。
5. 允许 A1 结束后，A2 才能开始。
6. 即使 A1 以异常结束，A2 仍必须继续执行。

## 题目四：并发定时任务调度器

### 题目描述与接口

实现 `TimerScheduler`，使用一个内部线程串行执行定时回调：

```text
using Clock = std::chrono::steady_clock;
using TaskId = std::uint64_t;
using Task = std::function<void()>;

TaskId schedule(Clock::time_point deadline, Task task);
bool cancel(TaskId id);
bool reschedule(TaskId id, Clock::time_point newDeadline);
void shutdown();
~TimerScheduler();
```

所有公开接口允许外部线程并发调用。TaskId 从 1 开始分配，不重复使用，也不回绕；按成功接受任务的顺序递增。

### 调度与修改

1. 不得早于 deadline 开始回调。截止时间已到或早于当前时间时，任务立即具备执行资格。
2. 操作系统调度或前一个回调可能导致延迟，不要求精确到某个时间误差以内。
3. 每次选择下一个回调时，在当时已接受、尚未开始且未取消的任务中，选择 deadline 最早者；相同 deadline 按 TaskId 升序。
4. 新加入的更早任务、取消和重新调度，都必须影响后续任务选择，不能继续仅按旧安排等待。
5. 同一任务最多执行一次，不周期性重复。
6. 回调异常不得使调度线程退出，也不得阻止其他任务执行；本题不要求通过接口返回回调异常。

任务开始执行时，从待执行状态转为运行状态：

- `cancel` 只有在任务仍待执行时才能返回 `true`，且返回 `true` 后该任务永远不会执行。
- 运行中、已完成、已取消或未知 ID，`cancel` 返回 `false`。
- `reschedule` 只有在任务仍待执行时返回 `true`，更新 deadline 并保留原 TaskId；其他情况返回 `false`。
- 截止时间已到但尚未开始的任务，仍可以被成功取消或重新调度。
- 修改与开始执行重叠时，以哪个操作先对该任务生效决定结果。

### 关闭

- `shutdown` 拒绝新任务，取消全部尚未开始的任务，并等待正在运行的回调结束、内部线程回收后返回。
- 不得为了已经取消的未来任务，等待到其原 deadline。
- 关闭后 `schedule` 抛出 `ComponentClosed`；`cancel`、`reschedule` 返回 `false`。
- 支持并发、重复关闭；析构具有完成一次 `shutdown` 的效果。

### 行为示例

**场景 A：更早任务改变等待安排。**

先添加一个很晚才到期的任务 A。调度器等待期间，添加更早到期的 B。

结果：B 到期后应能先执行；不能等到 A 的原截止时间才处理 B。

**场景 B：运行中不能取消。**

任务 A 已进入回调，等待测试程序允许其继续。此时 `cancel(A)` 返回 `false`，不得报告已成功阻止 A 执行。

**场景 C：重新调度仍待执行的任务。**

任务 A 尚未开始，`reschedule(A, laterDeadline)` 返回 `true`。

结果：A 不得在旧 deadline 开始，最早执行时刻改为 laterDeadline。

## 题目五：并行处理与保序输出

### 题目描述与接口

实现 `OrderedProcessor`。多个线程可以提交字符串输入，固定工作线程并行计算结果，单个消费线程按接受顺序获取结果。

```text
using Processor = std::function<std::int64_t(const std::string&)>;

struct Result {
    std::uint64_t seq;
    std::optional<std::int64_t> value;
    std::exception_ptr error;
};

OrderedProcessor(std::size_t workerCount,
                 std::size_t maxInFlight,
                 Processor processor);

std::uint64_t submit(std::string input);
std::optional<Result> next();
void close();
void join();
~OrderedProcessor();
```

`workerCount`、`maxInFlight` 均大于 0，processor 非空。输入允许为空字符串。测试程序保证 processor 可被并发调用。

### 接受与在途数量

1. 输入被成功接受时，分配从 1 开始连续递增的 seq，不回绕。
2. 重叠提交的接受顺序可以任意确定；互不重叠的成功提交必须保持先后关系。
3. 每个已接受输入恰好调用一次 processor。
4. 在途数量包含：排队中、计算中，以及计算结束但尚未被 `next` 取走的全部输入。
5. 在途数量达到 maxInFlight 时，新的 `submit` 等待，直到结果被取走而释放名额，或组件关闭。
6. 关闭后尚未接受的提交抛出 `ComponentClosed`，不占用 seq，也不调用 processor。

### 结果与输出顺序

- 计算成功：Result.value 为结果，Result.error 为空。
- 计算失败：Result.value 为空，Result.error 保存原异常。
- 某个输入失败，不得导致其 seq 缺失，也不得终止其他输入的计算。
- `next` 只能由一个消费线程调用，每次按 seq 升序取走一个结果；不能跳过尚未完成的较小 seq。
- 下一个结果尚未完成时，`next` 等待，即使更大 seq 已经完成。
- 组件仍开放、目前没有可返回结果时，`next` 等待更多输入或关闭。
- 已关闭且全部已接受结果均已取走时，`next` 返回 `std::nullopt`。
- 返回的 Result 自行持有其值或异常信息，组件销毁后仍可使用。

### 关闭、等待与析构

- `close` 停止接受输入并唤醒等待提交者，本身不等待已接受工作完成。
- 已接受输入仍须完成处理，其结果仍可按序读取。
- `join` 隐含执行 close，并等待全部已接受输入处理完成、回收工作线程后返回；不消费或丢弃结果。
- `join` 的完成不得依赖消费线程已经取走全部结果。它返回后，仍可调用 `next` 获取剩余结果。
- 允许并发、重复调用 close 或 join；每次 join 返回均表示全部工作线程已回收。
- 析构完成 join，并释放尚未取走的结果。

### 行为示例

maxInFlight 为 3，工作线程数至少为 2：

1. 成功接受三条输入，seq 分别为 1、2、3。
2. seq 1 正在计算；seq 2 已失败；seq 3 已成功，结果为 30。
3. 此时 `next` 必须等待 seq 1，不能先返回 seq 2 或 3。
4. 第四条输入的提交因在途数量已满而等待。
5. seq 1 完成并由 `next` 取走后，第四条提交才有机会获得空余名额。
6. 后续 `next` 依次返回 seq 2 的异常结果和 seq 3 的成功结果。
7. 调用 join 后，即使还有结果尚未读取，也必须能在全部计算结束后完成返回。

若步骤 4 的提交尚未被接受时发生关闭，该提交应被拒绝，而不是获得新的 seq。

## 规模与相关练习

- 工作线程数：1～32。

- 每组请求、任务或输入总数：不超过 `2 × 10^5`。
