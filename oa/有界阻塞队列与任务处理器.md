# 有界阻塞队列与任务处理器

**Bounded Blocking Queue & Task Executor**

> 自拟 C++17 多线程 OA 练习，建议限时 120 分钟，并非已核实的 DRW 或其他公司的原题。并发、关闭及异常语义均以本文为准。

## 题目

实现两个组件：

1. 支持多生产者、多消费者、固定容量和关闭操作的有界阻塞队列。
2. 使用固定数量工作线程执行任务的任务处理器，支持有界等待队列、结果获取、异常传播和安全关闭。

本题采用**接口调用形式**。测试程序会从多个真实线程调用接口，不设置标准输入、标准输出协议。行为示例用于规定可观察结果，不要求打印示例中的文字。

提交可编译的 C++17 实现。可以附带本地测试入口，接口行为必须满足下文约定。

## 1. 共同约定

- 两个组件均不可复制、不可移动。
- 所有允许并发调用的接口都必须避免数据竞争、资源泄漏和内部死锁。
- 条件不满足时，阻塞接口应等待条件发生变化，不得依靠持续轮询维持等待。
- 不要求不同等待线程之间的公平性，也不规定操作系统调度顺序。
- 测试保证所有可运行线程持续获得执行机会；任务最终正常返回或抛出异常，不存在用户任务之间的循环等待。
- 运行环境提供足够的内存和系统线程资源。
- 对象构造完成后才会被其他线程使用。
- 对象析构期间，不会有外部线程正在调用或新调用该对象的成员函数；任务处理器自身的工作线程由其负责回收。

## 2. 第一部分：有界阻塞队列

### 2.1 接口

接口形式如下；只规定公开调用方式，不规定内部成员布局：

```text
template<class T>
class BoundedBlockingQueue {
public:
    explicit BoundedBlockingQueue(std::size_t capacity);
    ~BoundedBlockingQueue();

    bool push(T value);
    std::optional<T> pop();
    void close();
};
```

类型 `T` 满足：

- 可以移动构造，且移动构造不抛出异常。
- 析构不抛出异常。
- 可能不可复制，也可能没有默认构造函数。
- 不要求支持移动赋值。

### 2.2 构造与容量

- `capacity > 0`，否则抛出 `std::invalid_argument`。
- 初始队列为空，状态为 `OPEN`。
- 容量固定，表示**已入队但尚未出队**的元素数量上限。
- 正在调用 `push` 但尚未入队的参数，不计入队列大小。

### 2.3 入队

```text
bool push(T value)
```

- 队列为 `OPEN` 且有空间时，接受一个元素，放入队尾，返回 `true`。
- 队列为 `OPEN` 且已满时，调用阻塞，直到可以成功入队，或队列关闭。
- 队列已关闭，或等待期间关闭生效且本元素尚未入队时，返回 `false`，不得把该元素加入队列。
- 返回 `true` 的元素只能入队一次。

参数按值传入。`push` 返回 `false` 时，不要求调用方此前传入的源对象保持原值，也不返回传入元素。

### 2.4 出队

```text
std::optional<T> pop()
```

- 队列非空时，移除队首元素并返回包含该元素的 `optional`。
- 队列为空且为 `OPEN` 时，调用阻塞，直到有元素，或队列关闭。
- 队列已关闭但仍有元素时，继续正常出队。
- 队列已关闭且为空时，返回 `std::nullopt`。

`std::nullopt` 只表示“队列已经关闭且没有剩余元素”，不能用它表示临时为空。

每个成功入队的元素，最多由一次成功 `pop` 取得。

### 2.5 关闭

```text
void close()
```

关闭操作具有以下语义：

1. 将队列从 `OPEN` 改为 `CLOSED`，状态不可恢复。
2. 拒绝关闭生效后尚未入队的新元素。
3. 使所有因队列已满而等待的生产者有机会返回 `false`。
4. 使所有因队列为空而等待的消费者有机会继续执行；没有剩余元素时返回 `std::nullopt`。
5. 已经入队的元素保持可用，按 FIFO 规则取出。

`close` 不等待队列排空，也不等待消费者完成处理。

允许多个线程同时调用 `close`，也允许重复关闭；每次调用均正常返回。

### 2.6 FIFO 与并发顺序

`push`、`pop` 和 `close` 必须具有可线性化的行为：

> 对这些操作，必须存在一个满足上述队列规则的顺序执行结果，并且不颠倒互不重叠调用的先后关系。

例如：

- 若 `push(A)` 已返回 `true`，之后才调用 `push(B)`，且后者也成功，则 A 必须先于 B 出队。
- 两个 `push` 调用重叠时，可以任意一个先入队，不按线程编号或函数调用开始时间排序。
- 两个 `pop` 调用重叠时，其返回到调用方的先后，不必等于元素在队列内部出队的先后。
- `push` 与 `close` 重叠时，入队先于关闭生效则可返回 `true`；关闭先于入队生效则必须返回 `false`。
- `close` 已返回后才开始的任何 `push`，必须返回 `false`。

### 2.7 队列生命周期

队列析构前，调用方保证所有外部接口调用已经结束。

析构时允许仍有未取出的元素；必须释放这些元素持有的资源。不能要求队列析构函数通过销毁对象来安全中断仍在使用该对象的外部线程。

## 3. 第二部分：固定线程任务处理器

### 3.1 接口

```text
class TaskExecutor {
public:
    using Task = std::function<std::int64_t()>;

    TaskExecutor(std::size_t workerCount, std::size_t capacity);
    ~TaskExecutor();

    std::future<std::int64_t> submit(Task task);
    void shutdown();
};
```

同时提供异常类型 `ExecutorClosed`，公开继承自 `std::runtime_error`。`what()` 的具体文本不作要求。

任务处理器的等待队列必须符合第一部分规定的容量、FIFO 和关闭语义。

### 3.2 构造与线程数量

- `workerCount > 0` 且 `capacity > 0`，否则抛出 `std::invalid_argument`。
- 构造成功后，处理器拥有固定的 `workerCount` 个工作线程，初始接受任务。
- `capacity` 只限制**已接受但尚未被工作线程取走**的任务数量，不包含正在执行的任务。
- 单个工作线程同一时刻只执行一个任务。
- 多个工作线程必须能够并发执行不同任务，不得把全部用户任务强制串行执行。
- 每次提交不得额外创建一个专门执行该任务的线程。

题目中的 `submit`、`shutdown` 及任务处理器析构均由工作线程之外的线程调用。任务不会调用所属处理器的这些接口，也不会等待同一处理器中其他任务的结果。

### 3.3 提交任务

```text
std::future<std::int64_t> submit(Task task)
```

- 空的 `std::function` 是非法参数，抛出 `std::invalid_argument`；即使处理器已经关闭，也先按此规则判定。
- 处理器仍接受任务且等待队列有空间时，接受任务，并返回与本任务对应的 `future`。
- 处理器仍接受任务但等待队列已满时，提交调用阻塞，直到能够接受任务，或关闭生效。
- 关闭已经生效，或等待期间关闭生效且本任务尚未被接受时，抛出 `ExecutorClosed`。
- 被拒绝的任务不得执行，也不会返回一个可供调用方获取的 `future`。

一个任务是否已被接受，以其成功加入等待队列为准，不以 `submit` 开始调用或返回到调用方的时间为准。

成功接受的任务必须恰好执行一次。任务可以在 `submit` 返回前已经开始执行，甚至已经结束。

### 3.4 结果与任务异常

- 任务正常返回 `std::int64_t` 时，对应 `future.get()` 返回该结果。
- 任务抛出异常时，对应 `future.get()` 重新抛出该异常，保持原异常类型及可观察信息。
- 某个任务失败，不得使工作线程退出，不得丢弃其他已接受任务，也不得让其他任务的结果永远无法获取。
- 调用方不获取某个 `future`，不会取消对应任务。
- `future` 可以在任务处理器析构后继续使用；已执行任务的结果仍应可获取。

### 3.5 任务顺序

任务的**出队顺序**遵守第一部分的 FIFO 规则。

多个工作线程的任务开始执行顺序、执行过程和完成顺序均不作保证。不能根据 FIFO 推断所有结果按提交顺序就绪。

调用方通过每次 `submit` 返回的独立 `future` 获取该任务结果，不按完成顺序重新分配结果。

### 3.6 关闭与等待完成

```text
void shutdown()
```

调用后必须完成以下行为：

1. 停止接受新任务。
2. 使尚未被接受、正在等待队列空间的提交调用结束，并抛出 `ExecutorClosed`。
3. 保留并执行所有已接受任务，包括当前排队任务和正在执行的任务。
4. 等待这些任务全部结束，并回收所有工作线程后才返回。

关闭不取消已接受任务，不强行中断正在执行的任务。

允许多个外部线程同时调用 `shutdown`，也允许在关闭完成后再次调用：

- 所有调用最终都应正常返回。
- 每个调用返回时，所有已接受任务都已结束，其结果或异常已可获取，工作线程已全部回收。
- 已关闭的处理器不可重新启动。

`submit` 与 `shutdown` 允许重叠。若任务先被接受，则必须完成；若关闭先于任务接受生效，则必须拒绝。

关闭生效后，等待队列空间的提交线程不能因用户任务尚未结束而继续等待空位。即使已有任务暂时阻塞，该提交也必须有机会观察关闭并拒绝。

### 3.7 析构

析构具有与完成一次 `shutdown` 相同的效果：

- 所有已接受任务执行完毕。
- 所有工作线程退出并被回收。
- 析构函数不向调用方抛出异常。
- 工作线程不得在对象存储已经释放后继续访问其成员。

调用方保证析构开始时，不再有其他外部接口调用正在进行，也不会发起新调用。若此前已完成 `shutdown`，析构仍应正常完成。

## 4. 测试规模与判定

- 队列及任务处理器容量范围为 `1～10^5`，另外测试非法的零容量。
- 工作线程数量范围为 `1～32`，另外测试非法的零工作线程数。
- 外部生产者或提交线程最多 16 个。
- 同一对象上的并发 `close` 或 `shutdown` 调用最多 4 个。
- 一组测试中的入队或任务提交次数不超过 `2 × 10^5`。
- 队列会测试整数及不可复制的资源持有类型。
- 任务会测试正常返回、抛出异常，以及由测试程序协调后才继续执行的情况。

不要求固定的线程调度顺序。只要结果符合所有接口规则和合法并发顺序，即可接受。

测试会检查：容量上限、FIFO、元素或任务的唯一性、关闭与提交竞争、等待线程退出、结果归属、异常传播，以及资源生命周期。

## 5. 行为示例

以下示例中的“等待”表示调用尚未返回。“协调后”表示示例明确规定了操作之间的先后关系；未规定的线程交错不作为判定条件。

示例中的线程名称只是标识，不表示执行优先级。

### 示例一：满队列等待、关闭后排空

创建容量为 2 的整数队列。

| 步骤 | 线程 | 操作或观察 | 必须满足的结果 |
| --- | --- | --- | --- |
| 1 | P0 | 调用 `push(101)` 并等待其返回 | 返回 `true` |
| 2 | P0 | 调用 `push(102)` 并等待其返回 | 返回 `true` |
| 3 | P1 | 调用 `push(103)` | 队列仍满，调用等待 |
| 4 | C0 | 调用 `pop()` | 返回 101 |
| 5 | P1 | 获得执行机会，完成步骤 3 的调用 | 返回 `true` |
| 6 | P0 | 在步骤 5 完成后调用 `close()` | 正常返回 |
| 7 | C0 | 调用 `pop()` | 返回 102 |
| 8 | C0 | 再调用 `pop()` | 返回 103 |
| 9 | C0 | 再调用 `pop()` | 返回 `std::nullopt` |
| 10 | P0 | 调用 `push(104)` | 返回 `false` |
| 11 | P0 | 再次调用 `close()` | 正常返回 |

### 示例二：关闭时存在等待者

两个子场景独立运行。

**场景 A：生产者正在等待。**

1. 创建容量为 1 的队列。
2. `push(7)` 成功返回。
3. 另一生产者调用 `push(8)`，因队列满而等待。
4. 调用 `close()` 并等待其返回。
5. 步骤 3 的调用最终返回 `false`。
6. 消费者依次调用两次 `pop()`，分别取得 7 和 `std::nullopt`。

元素 8 不得出现。步骤 5 与步骤 6 的实际执行先后可以交换，不影响结果。

**场景 B：多个消费者正在等待。**

1. 创建一个空的、尚未关闭的队列。
2. 两个消费者分别调用 `pop()`，均等待。
3. 调用 `close()`。
4. 两个消费者最终都返回 `std::nullopt`，返回先后不作要求。

### 示例三：任务结果、异常与并行执行

创建 `workerCount = 2`、`capacity = 2` 的任务处理器。

| 步骤 | 操作或协调条件 | 必须满足的结果 |
| --- | --- | --- |
| 1 | 提交任务 A，取得 `futureA` | 任务 A 被接受 |
| 2 | 等待 A 进入任务体；A 此后等待测试程序允许其继续 | 此时 A 尚未结束 |
| 3 | 提交任务 B，任务体直接返回 17，取得 `futureB` | B 被接受 |
| 4 | 测试程序仍未允许 A 继续，获取 B 的结果 | `futureB.get()` 返回 17 |
| 5 | 提交任务 C，任务体抛出 `std::runtime_error("boom")` | C 被接受 |
| 6 | 测试程序仍未允许 A 继续，获取 C 的结果 | 对应 `future.get()` 抛出 `std::runtime_error`，信息为 `boom` |
| 7 | 允许 A 继续；A 返回 11；调用 `shutdown()` 并等待返回 | 关闭正常完成 |
| 8 | 获取 A 的结果 | `futureA.get()` 返回 11 |
| 9 | 提交一个合法的非空任务 | 抛出 `ExecutorClosed`，该任务不执行 |
| 10 | 再次调用 `shutdown()` | 正常返回 |

A 尚未结束时，B、C 仍必须能够由另一个工作线程执行。

### 示例四：提交阻塞与并发关闭

创建 `workerCount = 1`、`capacity = 1` 的任务处理器。

1. 提交任务 A，取得 `futureA`；等待 A 进入任务体。
2. A 等待测试程序允许其继续，之后将返回 100。
3. 提交任务 B，取得 `futureB`；B 的任务体返回 200。此时 B 留在等待队列中。
4. 外部线程 P 提交任务 C。由于唯一工作线程仍执行 A，且等待队列中已有 B，P 的提交等待。
5. 两个外部线程 S1、S2 调用 `shutdown()`。在 A 尚未被允许继续的条件下，P 必须最终抛出 `ExecutorClosed`，C 不得执行。
6. 此时 S1、S2 都不能完成返回，因为 A 尚未结束。
7. 测试程序在观察到 P 已被拒绝后，允许 A 继续。
8. A 返回 100，随后 B 被执行并返回 200。
9. S1、S2 最终都正常返回；两者返回先后不作要求。
10. `futureA.get()` 返回 100，`futureB.get()` 返回 200。

关闭过程中，B 不得被丢弃，C 不得变为已接受任务，也不能要求先结束 A 才能拒绝 P。
