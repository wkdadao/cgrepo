# FIX 4.4 消息解析与构造

> 自拟 C++ OA 练习，建议核心部分限时 120 分钟，并非已确认的 DRW 原题。本文定义一个有限的 FIX 4.4 消息子集；字段范围、输入输出和额外限制以本文为准，不要求实现完整 FIX engine。

## 题目

实现消息构造和消息解析程序，支持：

| 操作 | MsgType | 消息 |
| --- | --- | --- |
| 构造 | `D` | NewOrderSingle |
| 构造 | `F` | OrderCancelRequest |
| 构造 | `G` | OrderCancelReplaceRequest |
| 解析 | `8` | ExecutionReport |
| 解析 | `9` | OrderCancelReject |

程序不维护订单，不撮合，不连接网络，不生成当前时间或自动递增序号。每条核心输入独立处理，不根据历史消息判断序号是否连续或请求是否重复。

## 消息表示

实际消息的字段形式为：

```text
tag=value<SOH>
```

`SOH` 是一个值为 `0x01` 的字节。

为方便文本输入输出，本题命令行中使用 `|` 表示 SOH。**长度和校验和必须按替换为 SOH 后的真实字节计算**；不得按字符 `|` 的字节值计算校验和。

所有输入消息和字段值仅使用 ASCII。普通字段值非空，不包含空白或 `|`，可以包含 `=`。字段 tag 是无前导零的正十进制整数。

不支持 Repeating Groups、Length/Data 字段、二进制值或加密字段。

## 消息结构及校验

### Header 和 Trailer

消息开头的三个字段依次是：

```text
8=FIX.4.4|9=BodyLength|35=MsgType|
```

此外必须具有 `49`、`56`、`34`、`52` 四个头部字段，且它们位于所有业务字段之前；解析时，这四个字段之间的顺序可不同。

消息最后一个字段必须是：

```text
10=ddd|
```

`ddd` 为三位十进制数字，数值范围为 0～255，不足三位补零。其后不能有额外字节。消息必须保留最后一个字段分隔符。

同一条消息中的任何 tag 均不得重复，包括 Header、业务字段和 Trailer。

### BodyLength(9)

数值为：从 `9=...<SOH>` 之后的第一个字节开始，到 `10=` 之前的最后一个 SOH 为止，包含这两个端点的总字节数。

### CheckSum(10)

数值为：从消息开头的 `8` 字节开始，到 `10=` 之前的最后一个 SOH 为止，所有字节的无符号数值之和对 256 取模。

### 通用字段

| Tag | 名称 | 本练习中的合法值 |
| --- | --- | --- |
| 8 | BeginString | 固定为 `FIX.4.4` |
| 9 | BodyLength | 非负十进制整数，必须与实际长度一致 |
| 35 | MsgType | 构造为 `D/F/G`；解析为 `8/9` |
| 49 | SenderCompID | ID |
| 56 | TargetCompID | ID |
| 34 | MsgSeqNum | 正整数，不超过 `10^9` |
| 52 | SendingTime | 时间戳 |
| 10 | CheckSum | 上述三位十进制校验值 |

## 业务字段

### 字段类型

| 类型 | 限制 |
| --- | --- |
| ID | 长度 1～32，仅含字母、数字、下划线或连字符 |
| 正数量 | 十进制整数，范围 1～`10^9` |
| 非负数量 | 十进制整数，范围 0～`10^9` |
| 正价格 | 大于 0、不超过 `10^6` 的十进制数，最多四位小数 |
| 非负价格 | 大于等于 0、不超过 `10^6` 的十进制数，最多四位小数 |
| 时间戳 | 固定形式 `YYYYMMDD-HH:mm:ss.SSS`，数字位必须为数字；不要求校验日历及时间取值 |

数量和价格不得包含正负号、科学计数法或非数字后缀。小数点后必须有 1～4 位数字；整数形式的价格也合法。数值允许前导零，输入的原始数值文本必须保留，不改变小数位数。

### 支持的字段表

| Tag | 名称 | 类型或合法值 |
| --- | --- | --- |
| 6 | AvgPx | 非负价格 |
| 11 | ClOrdID | ID |
| 14 | CumQty | 非负数量 |
| 17 | ExecID | ID |
| 31 | LastPx | 正价格 |
| 32 | LastQty | 正数量 |
| 37 | OrderID | ID |
| 38 | OrderQty | 正数量 |
| 39 | OrdStatus | `0/1/2/4/6/8/E` |
| 40 | OrdType | 固定为 `2`，表示 Limit |
| 41 | OrigClOrdID | ID |
| 44 | Price | 正价格 |
| 54 | Side | `1` 买，`2` 卖 |
| 55 | Symbol | ID |
| 60 | TransactTime | 时间戳 |
| 102 | CxlRejReason | 0～`10^9` 的整数 |
| 150 | ExecType | `0/4/5/6/8/E/F` |
| 151 | LeavesQty | 非负数量 |
| 434 | CxlRejResponseTo | `1` 撤单，`2` 改单 |

本文允许的 `ExecType` 分别表示 New、Canceled、Replaced、PendingCancel、Rejected、PendingReplace、Trade。

本文允许的 `OrdStatus` 分别表示 New、PartiallyFilled、Filled、Canceled、PendingCancel、Rejected、PendingReplace。

另允许 tag 为 `5000～9999` 的扩展普通字段。这些字段仍需非空且不重复，但不校验其值的业务类型。其他未列出的标准 tag 不在本题支持范围，出现时视为错误。

### 每种消息的必填业务字段

下表为本练习限定的必填集合，不代表 FIX 标准对全部场景的完整条件要求。

| MsgType | 必填业务 tag |
| --- | --- |
| `D` | `11, 38, 40, 44, 54, 55, 60` |
| `F` | `11, 38, 41, 54, 55, 60` |
| `G` | `11, 38, 40, 41, 44, 54, 55, 60` |
| `8` | `6, 11, 14, 17, 37, 38, 39, 54, 55, 150, 151` |
| `9` | `11, 37, 39, 41, 102, 434` |

`35=8` 且 `150=F` 时，还必须提供 `31` 和 `32`。

本题允许上述字段表中的其他业务字段作为可选字段出现；若出现，仍按其类型验证。除此之外，不校验跨字段业务关系、订单状态转换或所有 FIX 条件必填规则。

## 构造命令

```text
BUILD msgType seqNum sender target sendingTime tag=value tag=value ...
```

命令提供 Header 的五个输入值及业务字段。业务字段输入顺序任意。

不得在业务字段列表中提供 `8/9/35/49/56/34/52/10`；不得覆盖 Header 或 Trailer。

合法时输出一行完整消息，分隔符展示为 `|`，字段顺序固定为：

1. Header：`8, 9, 35, 49, 56, 34, 52`。
2. 所有业务字段按 tag 数值升序排列。
3. Trailer：`10`。

`8` 固定为 `FIX.4.4`；`9` 和 `10` 由程序生成。其他字段值保留输入文本。

不合法时输出一行：

```text
ERROR
```

## 解析命令

```text
PARSE message
```

`message` 为一条以 `|` 展示 SOH 的完整消息。程序应验证本题规定的结构、字段类型、必填字段、长度及校验和。

合法时输出：

```text
PARSED msgType tag=value tag=value ...
```

输出仅包含业务字段，按 tag 数值升序排列，扩展普通字段也包含在内；不输出 Header 和 Trailer。字段值保留原文，各项之间恰好一个空格，无行末空格。

不合法时输出一行 `ERROR`。无需区分错误原因，失败消息不产生部分解析结果。

## 输入输出与规模

- 从标准输入逐行读取核心命令，直到 EOF。
- 命令名仅为 `BUILD` 或 `PARSE`，没有空行；消息和字段可能非法、缺失或截断。
- 对每条核心命令恰好输出一行，错误后继续处理下一条命令。
- 单条编码后的消息最长 1 MiB；一条消息最多 256 个字段。
- 输入最多 `10^4` 条命令，总消息文本大小不超过 20 MiB。
- 只允许使用 C++ 标准库；不得使用现成 FIX 编解码库。
- 不得输出调试日志或额外解释。

## 样例一：构造消息

### 输入

```text
BUILD D 1 CLIENT VENUE 20261017-03:30:00.000 11=N1 55=XYZ 54=1 60=20261017-03:30:00.000 38=100 40=2 44=12.50
BUILD D 2 CLIENT VENUE 20261017-03:30:00.000 11=N2 55=XYZ 54=1 60=20261017-03:30:00.000 38=100 40=2
```

### 输出

```text
8=FIX.4.4|9=118|35=D|49=CLIENT|56=VENUE|34=1|52=20261017-03:30:00.000|11=N1|38=100|40=2|44=12.50|54=1|55=XYZ|60=20261017-03:30:00.000|10=085|
ERROR
```

## 可选扩展：分片输入

这一部分独立计时，不计入核心两小时任务。

扩展模式的输入仅包含若干条 `FEED`，最后一条为 `END`：

```text
FEED chunk
END
```

每个非空 `chunk` 是消息字节流的一部分，仍用 `|` 表示 SOH。按输入顺序连接所有 chunk 后，得到若干条完整消息，以及可能存在的最后一条未完成消息。

分片可能发生在任意字节位置，包括 tag、数值、长度和校验和内部。一个 chunk 也可能含有多条消息。

- 每收到一条完整消息，立即按核心 `PARSE` 规则输出一行。
- 尚未收到完整消息时，不输出。
- `END` 时仍有未完成消息，输出一行 `ERROR`；没有剩余数据则不输出。
- 完整消息保证属于本文合法的 `8/9` 消息；无需实现损坏字节流的重新同步。
- 本扩展不增加 Logon、Heartbeat、Resend、SequenceReset、重连或真实 socket 要求。
