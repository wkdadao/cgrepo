# Push Box + Gravity — 推箱子与同步重力模拟

> **C1 / Simulation / Push Box + Gravity**  
> 建议用时：**75–90 分钟** ｜ 难度：**中高** ｜ 建议语言：**C++17/20**  
> 训练方向：**读题 → 建模 → 状态转移 → Event-Driven → Validation → 测试**  
> **本文件只包含完整题目、规则、样例及测试清单，不包含参考解法。**
>
> 本题是专为 OA 训练设计的改编题，**不声称复现 DRW 面试原题**。

## 1. Problem Statement

给定一个二维地图，包含一名玩家（`P`）、若干箱子（`B`）、不可移动的墙壁（`#`）以及空地（`.`）。

玩家接收由 `L`（向左）和 `R`（向右）组成的指令序列。玩家可以水平移动；如果前方是一个或多个连续箱子，可以尝试将它们整体水平推动一格。

每条指令中，一旦水平移动成功，**玩家和所有箱子都将受到重力影响**。重力以离散的同步时间步（gravity tick）推进，直到所有可动物体都不再下落。

**任务：判断整串指令是否能全部合法执行。**

- 如果每条指令都合法，输出 `VALID` 和最终地图。
- 如果某条指令不合法，输出 `INVALID i`，其中 `i` 是第一条失败指令的编号（从 1 开始）。
- 任一指令失败后，不再执行后面的指令；不输出部分完成的地图。

**注意：** 本题不要求把箱子推到目标位置，也没有计分机制；核心是准确模拟整串指令的合法性及最终状态。

## 2. 地图规则

地图有 `H` 行、`W` 列，均从 **1** 开始编号。每个格子只能包含下列字符：

| 字符 | 含义 |
|---|---|
| `#` | 固定墙壁，不可进入、不可移动 |
| `.` | 空地，可进入 |
| `P` | 玩家；恰好一个 |
| `B` | 箱子；至少一个，可以有多个 |

玩家与箱子都是**占据一个格子的可动物体**，任何时候不得重叠。

### 2.1 初始状态

输入保证：

- 恰好一个 `P`，至少一个 `B`。
- 所有物体的位置互不重叠，也不与墙重叠。
- **初始状态已处于重力稳定状态**：没有玩家或箱子能够立刻向下移动一格。

因此，程序**不需要在处理第 1 条指令前额外执行重力**。

地图**不保证**周围一定有一圈墙壁：水平移动到地图以外是非法的；但重力方向上的地图底边视为地面，物体可以停在最后一行，不会掉出地图。

## 3. 水平移动（Manual Movement）

每条指令是一个字符：

- `L`：玩家尝试向左移动一格。
- `R`：玩家尝试向右移动一格。

**本题没有上下移动，也没有玩家朝向属性。**

假设当前指令方向为 `dx`（左为 `-1`，右为 `+1`），玩家位于 `(r, c)`，目标是 `(r, c + dx)`。

### 3.1 目标为空地

玩家移动到目标格子；原位置变成空地。随后执行完整的重力阶段。

### 3.2 目标是墙壁或越界

整条指令**失败**；整串指令立即判定为非法。

不能把这次移动当成合法的 no-op。失败时不会额外触发重力。

### 3.3 目标是箱子

玩家可以推动**同一行、同一方向、连续相邻的所有箱子**，但这些箱子必须能够**一起向该方向移动一格**。

设连续箱子的最后一个后方格子为 `target`：

- 如果 `target` 是空地 `.`，推动成功。
- 如果 `target` 是墙壁 `#` 或地图边界外，推动失败。

推动成功时：

1. 整串连续箱子同时沿指令方向移动一格。
2. 玩家移动到最近一个箱子原来的位置。
3. 玩家原来的位置变为空地。
4. **整个水平推动完成后**，才开始重力阶段。

例如：

~~~text
Before:  #PBB..#
Command: R
After horizontal movement (before gravity):
         #.PBB.#
~~~

**不能**让某个箱子在水平推动链尚未完成时先下落，也不能把玩家先放进仍被箱子占据的位置并让后续操作意外读取这一临时重叠状态。

若推动失败，本条指令失败，整串指令立即终止。

## 4. 重力（Gravity）

**只有水平移动成功后，才触发重力。**

重力作用于**玩家及所有箱子**，持续到整个地图稳定为止。一个物体只会竖直向下运动，重力不会使它水平移动。

### 4.1 单次 Gravity Tick：同步更新

每一个 tick 必须遵循：

1. 从**当前 tick 开始时的地图快照**，检查每一个 `P` / `B`。
2. 如果某物体正下方一格**当前是 `.`**，它将在本 tick 向下移动一格。
3. 如果正下方是 `#`、`P`、`B`，或物体已在最后一行，则本 tick 不动。
4. **所有本 tick 允许下落的物体一起移动**；之后才开始下一个 tick。

换句话说，不能在扫描网格时移动一个物体后，立即让另一个物体依据“已经被修改的当前 tick”做决定。

### 4.2 同步语义示例

考虑同一列：

~~~text
Before tick:        After tick 1:      After tick 2:

    B                   B                   .
    B                   .                   B
    .                   B                   B
    #                   #                   #
~~~

- Tick 1：下方的箱子可以下落；上方的箱子**不能**进入“下方箱子将在本 tick 离开的格子”，因为开始时该格仍被占据。
- Tick 2：上方箱子才有机会下落。
- 箱子不会互相穿透、交换位置或重叠。

此示例只展示局部竖直重力行为；实际地图还包含玩家。

### 4.3 达到稳定状态

重复执行 gravity tick，直到某一 tick **没有任何物体移动**。

在稳定之前：

- **不能读取下一条用户指令**。
- **不能输出最终状态**。
- 玩家与箱子都被当作障碍物；一个物体会被其他物体支撑。

重力不会破坏墙壁，也不会创造或销毁玩家和箱子。

## 5. 整串指令的执行与失败规则

对指令 `command[1..Q]`，从左到右依次处理：

~~~text
For each command:
    1. Try horizontal movement / push
    2. If movement fails -> INVALID, stop immediately
    3. If movement succeeds -> apply gravity ticks until stable
    4. Continue with next command

If every command succeeds -> VALID + final grid
~~~

**合法性的定义非常严格**：即使前 `i−1` 条指令全部合法，只要第 `i` 条失败，整串指令就非法。

这与某些游戏里“撞墙就原地不动”的规则不同；此题**明确规定撞墙、越界或推动失败都是非法指令**。

## 6. 输入格式

~~~text
H W
grid[1]
grid[2]
...
grid[H]
Q
command[1]
command[2]
...
command[Q]
~~~

说明：

- `H W`：地图高、宽。
- `grid[i]`：长度恰为 `W` 的字符串。
- `Q`：指令数量。
- 每条 `command[i]` 是单独一行的 `L` 或 `R`。

输入只有**一组测试数据**；保证格式合法。

## 7. 输出格式

### 所有指令合法

先输出：

~~~text
VALID
~~~

接着输出 **H 行**最终地图，每行长度均为 `W`；地图字符格式与输入完全相同。

### 存在非法指令

只输出一行：

~~~text
INVALID i
~~~

`i` 是第一条非法指令的 **1-based** 序号。不要输出中间地图。

## 8. 数据范围

| 项目 | 限制 |
|---|---|
| 地图尺寸 | `3 ≤ H, W ≤ 30` |
| 指令数 | `1 ≤ Q ≤ 1,000` |
| 玩家数量 | 恰好 1 |
| 箱子数量 | 至少 1，其余由地图容量约束 |
| 输入地图 | 满足第 2.1 节的初始重力稳定保证 |
| 建议时间限制 | 2 秒 |
| 建议内存限制 | 256 MB |

允许使用直接遍历地图的朴素模拟。**不要求**提前优化为坐标索引、增量维护或复杂对象系统。

## 9. 样例

### Sample 1 — 推箱子离开平台，随后玩家下落

**Input**

~~~text
7 9
#########
#.......#
#..PB...#
#..##...#
#.......#
#.......#
#########
3
R
R
L
~~~

**Output**

~~~text
VALID
#########
#.......#
#.......#
#..##...#
#.......#
#...PB..#
#########
~~~

**Explanation**

使用 1-based 坐标：

- 初始玩家在 `(3,4)`，箱子在 `(3,5)`，两者下方均有墙支撑。
- 第 1 条 `R`：箱子被推到 `(3,6)`，玩家来到 `(3,5)`。重力使箱子掉落到 `(6,6)`；玩家仍被墙支撑。
- 第 2 条 `R`：玩家进入 `(3,6)`，随后下落到 `(5,6)`，被 `(6,6)` 的箱子支撑。
- 第 3 条 `L`：玩家移至 `(5,5)`，然后下落到 `(6,5)`，箱子仍在 `(6,6)`。

### Sample 2 — 连续箱子推动失败

**Input**

~~~text
5 9
#########
#.......#
#.......#
#..PBB.##
#########
3
R
R
L
~~~

**Output**

~~~text
INVALID 2
~~~

**Explanation**

- 第 1 条 `R`：玩家成功将两个相邻箱子一起右移一格。
- 第 2 条 `R`：两个箱子需要继续向右移动，但最后一个箱子右边是墙壁。
- 因此第 2 条指令失败，第 3 条 `L` 不再执行。

### Sample 3 — 箱子下落并堆叠，玩家受到箱子支撑

**Input**

~~~text
7 10
##########
#........#
#........#
#..PBB...#
#..###...#
#........#
##########
3
R
R
R
~~~

**Output**

~~~text
VALID
##########
#........#
#........#
#.....P..#
#..###B..#
#.....B..#
##########
~~~

**Explanation**

- 第 1 条 `R`：推动两个箱子。靠右箱子离开平台后下落到第 6 行；靠左箱子仍被平台支撑。
- 第 2 条 `R`：剩余上层箱子向右移至第 7 列，重力使它落在下方箱子的正上方（第 5 行）。
- 第 3 条 `R`：玩家移动到两个箱子正上方，被堆叠的箱子支撑，不能穿过它们。

### Sample 4 — 没有边框墙壁时的水平越界

**Input**

~~~text
3 4
....
P...
####
1
L
~~~

**Output**

~~~text
INVALID 1
~~~

**Explanation**

玩家起始于 `(2,1)`。向左会越过地图边界，因此第一条指令立即失败；**不能假设所有地图都被 `#` 包围**。

## 10. 必须独立测试的边界情况

1. 玩家面对墙壁，第一条指令就失败。
2. 玩家紧贴左 / 右边界，向边界外移动。
3. 玩家直接移动到空地，且不产生重力位移。
4. 玩家离开平台后下落多格。
5. 箱子被推出平台后下落多格。
6. 玩家下落后被箱子支撑。
7. 箱子下落后被另一个箱子支撑。
8. 推动一串长度大于 1 的箱子成功。
9. 推动一串箱子时，最远端被墙阻挡而失败。
10. 推动一串箱子时，最远端是地图边界外而失败。
11. 推动后出现多个物体在同一 tick 可下落，检查**同步**语义。
12. 下方物体在当前 tick 下落，上方物体不能同 tick 跟进。
13. 重力持续多个 tick，必须执行到全图稳定。
14. 某一条后续指令失败，正确输出**首次失败的指令编号**。
15. 地图没有外围墙壁，但重力底边仍可支撑物体。
16. 成功处理全部指令后，地图仍恰好包含一个玩家、原有数量的箱子。

## 11. OA 训练任务（不属于判题输入输出）

建议按以下顺序完成：

### Part A — Reading & Modeling（15 分钟）

先回答以下问题，不写 C++：

- 最小 `State` 需要保存哪些字段？哪些信息可以从地图获取？
- 什么叫“完成一条指令”？何时算成功？何时算失败？
- 连续推动箱子应作为一个原子动作还是多个可交错动作？
- Gravity 的同步 tick 与简单的“扫描时立即移动”有什么不同？
- 判断整串指令合法时，事务边界应如何定义？
- 哪些条件属于 Local Validation，哪些属于 Final-State Invariant？

### Part B — Implementation（45–55 分钟）

用 C++17/20 实现标准输入输出。

可以采用简单循环，也可以练习本目录的 **TEDS — Transactional Event-Driven Simulation**：

~~~text
Command Event
    |
    +-- Horizontal Move / Push (atomic)
    |
    +-- Gravity Tick
    |      |
    |      +-- If any object moved, schedule next Gravity Tick
    |
    +-- Validate stable state
    |
    +-- Next Command
~~~

**提示：** Event-Driven 不意味着必须使用 `priority_queue`。本题没有明确的事件时间戳，直接调用函数或 FIFO Queue 都是合理的；同步 gravity tick 的语义比具体容器更重要。

### Part C — Testing & Review（15–20 分钟）

- 手动跑通全部给定样例。
- 选出至少 5 个第 10 节中的边界情况，自己构造输入和预期输出。
- 检查整串指令失败时没有错误地输出最终地图。
- 检查是否对“重力直到稳定”及“同步更新”存在遗漏。
- 先保证正确性，再考虑性能和代码抽象。
