# Event-Driven Simulation — Elevator Request Scheduler

> **C1 / Simulation / Event-Driven**  
> 建议用时：**75–100 分钟** ｜ 难度：**中等偏上** ｜ 建议语言：**C++17/20**  
> 训练重点：事件时间线、事件调度、状态机、同时间戳排序、FIFO 请求队列、异步到达、测试验证  
> **本文件只有完整题目、样例和测试要求，不提供解法或 C++ 参考答案。**
>
> 本题是针对 OA 设计的**单电梯离散事件模拟**练习，并非真实电梯控制器的完整运行规则。

## 1. Problem Statement

一栋建筑共有 `F` 层楼，编号为 `1..F`，有**一台电梯**，初始位于楼层 `S`，在时间 `0` 时处于 **IDLE（空闲、门已关闭）** 状态。

系统会在不同时间收到乘客乘梯请求。第 `i` 条请求包含：

- `a[i]`：请求到达时间；
- `from[i]`：乘客所在楼层；
- `to[i]`：目标楼层。

每个请求代表一名乘客。电梯容量为 **1 人**，一次只能服务一条请求。系统严格按照 **FIFO（请求到达时间优先，相同时间按照输入 ID 优先）** 为请求提供服务。

电梯可能在接客途中、载客途中，或正在开门等待的过程中收到新请求。这些请求必须按规则进入等待队列，**不能抢占当前正在服务的请求**。

请按时间推进整个模拟，输出每条请求的**接客时间、送达时间、等待时间**，以及电梯的**总移动楼层数、完成全部工作的时间和最终楼层**。

## 2. 精确时间模型

所有时间均为**非负整数**，单位为秒。

- 电梯在相邻两层之间移动耗时 `T` 秒。
- 从楼层 `x` 移动到 `y` 耗时 `|x-y| * T` 秒。
- 移动 `|x-y|` 层，计入总移动楼层数 `|x-y|`，**无论是否载客**。
- 抵达接客楼层时，乘客**立即上电梯**；记录这个时刻为 `pickupTime`。
- 抵达目标楼层时，乘客**立即离开**；记录这个时刻为 `dropoffTime`。
- 每次乘客上电梯或离开电梯，电梯都需要 `D` 秒处理开门与关门；这段时间电梯**不可移动，也不可接下一位乘客**。
- 电梯在接客楼层的门操作完毕后才开始载客行驶；送达后的门操作完毕后才重新变成 IDLE。
- **无需单独计算电梯空驶到接客楼层后的开门时间之外的额外停靠时间**。

### 2.1 完整服务时间线

当电梯在时刻 `t` 空闲、位于楼层 `x`，并选中请求 `(a, from, to)`：

~~~text
t                     开始空驶去 from（若 x == from，则无需移动）
t + |x-from| * T      到达 from；乘客立即上梯 => pickupTime
pickupTime + D        接客开关门结束，开始载客行驶
pickupTime + D
    + |from-to| * T   到达 to；乘客立即离开 => dropoffTime
dropoffTime + D       送客开关门结束，电梯重新 IDLE
~~~

即：

~~~text
pickupTime  = t + abs(x - from) * T
dropoffTime = pickupTime + D + abs(from - to) * T
readyTime   = dropoffTime + D
waitTime    = pickupTime - a
~~~

上式只是**一条请求被派单时**的时间定义，并不是要求提前计算全部请求结果。请求何时被派单，取决于之前所有到达事件和电梯状态。

**没有其他时间消耗**：不计算启动加速度、楼层间停靠、按钮响应或乘客步行时间。

## 3. 请求队列与派单规则

每个请求具有唯一 ID，为输入顺序中的 `1,2,...,N`。

### 3.1 Request Arrival

请求在时间 `a[i]` 才正式进入系统：

1. 将请求加入等待队列。
2. 以 `(a[i], i)` 的字典序确定 FIFO 先后顺序。
3. 如果电梯已经在服务请求或门操作中，新请求**只进入队列**，不改变当前任务。

**输入请求行不保证按照到达时间排序。** 必须按 `(arrivalTime, requestId)` 来解释真正的到达顺序，而不是按输入顺序简单处理。

### 3.2 电梯空闲时派单

只要电梯处于 **IDLE** 且存在待服务请求：

1. 立即选择等待队列中的最早请求。
2. 电梯立即开始空驶到该请求的 `from` 楼层。
3. 一旦开始服务，不允许被后续请求抢占，直到把该乘客送达并完成送客门操作。
4. 如果电梯正好就在 `from` 楼层，**立刻**发生 Pickup，空驶距离与耗时都为 0。

如果等待队列为空，电梯保持 IDLE，**停在当前位置**，直到下一条请求到达。

### 3.3 忙碌期间的新请求

无论电梯处于：

- 正在空驶去接客；
- 接客后的门操作中；
- 正在载客行驶；
- 送达后的门操作中；

新到请求都只排队等待。

**不允许**改变当前目的地、提前顺路搭载其他乘客、同时服务多位乘客，也不允许取消已经开始的服务。

### 3.4 一个请求何时完成？

本题区分：

- **dropoffTime**：乘客抵达目标楼层并离开电梯；
- **readyTime**：送客开关门结束，电梯恢复空闲。

下一位乘客的服务**最早只能在 readyTime 开始**。

最后一个乘客离开电梯时，模拟仍需等待其最后 `D` 秒的门操作完成。

因此，最终的 **FINISH_TIME** 是**最后一次送客门操作结束的时刻**，不是最后一位乘客的 `dropoffTime`。

## 4. 同一时间戳的事件排序

多个事件可能发生在同一个时刻。为避免实现结果依赖容器迭代顺序，本题明确规定：

1. **首先**处理该时间戳的所有新请求到达事件，按请求 ID 递增顺序。
2. **其次**处理电梯到达接客楼层（Pickup）或目标楼层（Dropoff）的事件。
3. **最后**处理门操作结束（Ready）并检查是否需要派单。

如果在处理该时间戳的事件时生成了新的**同一时刻**事件（例如电梯已在待接客楼层，空驶耗时为 0），应继续处理它们，直到该时间点没有待处理事件，才能推进到更晚的时间。

此题只有一台电梯，因此同一时刻不会存在两个相互冲突的电梯移动事件。事件排序的主要目的，是确保**同时到达的请求先登记，再选择下一位乘客**。

**重要例子**：当一个请求在 `t=5` 到达，而电梯恰好在 `t=5` 完成门操作，必须先将该请求加入等待队列，再由电梯进行派单。

如果电梯原本就 IDLE，某个请求到达时可以立即触发派单；当同一时间有多个新请求，优先选择 ID 较小的请求。

## 5. 输入格式

~~~text
F S T D
N
a[1] from[1] to[1]
a[2] from[2] to[2]
...
a[N] from[N] to[N]
~~~

说明：

- `F`：建筑楼层数；
- `S`：电梯在 `t=0` 时的初始楼层；
- `T`：每移动一层所需时间；
- `D`：每次乘客上梯或下梯的开关门耗时；
- `N`：请求数量；
- 第 `i` 行请求定义 ID 为 `i`。

输入保证格式有效，`from[i] != to[i]`，所有楼层都在合法范围内。

## 6. 输出格式

先输出 `N` 行，每行按**输入 ID 顺序**输出：

~~~text
pickupTime[i] dropoffTime[i] waitTime[i]
~~~

接着输出三行：

~~~text
TOTAL_DISTANCE X
FINISH_TIME Y
END_FLOOR Z
~~~

其中：

- `X`：从时间 0 到全部请求完成，电梯**空驶 + 载客**累计移动的楼层数。
- `Y`：最后一次送客门操作完成的时间。
- `Z`：全部工作完成后电梯所在的楼层。

所有整数均使用十进制，不输出标题、乘客 ID 或额外日志。时间和距离可能较大，使用 64-bit 整数存储。

## 7. 数据范围

| 项目 | 约束 |
|---|---|
| `2 ≤ F ≤ 100,000` | 总楼层 |
| `1 ≤ S ≤ F` | 初始楼层 |
| `1 ≤ T ≤ 100` | 每层耗时 |
| `1 ≤ D ≤ 100` | 上梯/下梯开关门耗时 |
| `1 ≤ N ≤ 200,000` | 请求数 |
| `0 ≤ a[i] ≤ 10^9` | 请求到达时间 |
| `1 ≤ from[i], to[i] ≤ F` | 起点与终点 |
| `from[i] != to[i]` | 必须有实际行程 |
| 建议时间限制 | 2 秒 |
| 建议内存限制 | 256 MB |

注意：即使单次行程较短，大量请求的累计完成时间也可能超过 32-bit 有符号整数范围。

## 8. 样例与详细解释

### Sample 1 — 忙碌期间请求持续到达

**Input**

~~~text
8 3 2 1
4
0 3 6
0 5 2
4 7 8
15 2 4
~~~

**Output**

~~~text
0 7 0
10 17 10
28 31 24
44 49 29
TOTAL_DISTANCE 21
FINISH_TIME 50
END_FLOOR 4
~~~

**Explanation**

`T=2` 秒/层，`D=1` 秒。

| ID | 请求到达 | 开始接客 | 送达 | 完成送客门操作 |
|---|---:|---:|---:|---:|
| 1 | 0 | 0 | 7 | 8 |
| 2 | 0 | 10 | 17 | 18 |
| 3 | 4 | 28 | 31 | 32 |
| 4 | 15 | 44 | 49 | 50 |

事件时间线：

~~~text
t=0   #1、#2 请求到达；服务 #1，在 3 楼立刻接客
t=1   #1 完成接客门操作，3 -> 6
t=4   #3 请求到达，等待
t=7   #1 到达 6 楼并下梯
t=8   电梯 Ready，开始空驶 6 -> 5 去接 #2
t=10  #2 上梯
t=11  #2 开始载客 5 -> 2
t=15  #4 请求到达，等待
t=17  #2 下梯
t=18  电梯 Ready，开始空驶 2 -> 7 去接 #3
t=28  #3 上梯
t=29  #3 开始载客 7 -> 8
t=31  #3 下梯
t=32  电梯 Ready，开始空驶 8 -> 2 去接 #4
t=44  #4 上梯
t=45  #4 开始载客 2 -> 4
t=49  #4 下梯
t=50  最后一次门操作结束
~~~

累计距离：

~~~text
#1: empty 0 + loaded 3
#2: empty 1 + loaded 3
#3: empty 5 + loaded 1
#4: empty 6 + loaded 2
TOTAL_DISTANCE = 21
~~~

### Sample 2 — 请求恰在 Ready 时到达，同时间请求按 ID 排序

**Input**

~~~text
5 2 1 2
3
0 2 3
5 1 4
5 4 2
~~~

**Output**

~~~text
0 3 0
7 12 2
14 18 9
TOTAL_DISTANCE 8
FINISH_TIME 20
END_FLOOR 2
~~~

**Explanation**

- #1 在 `t=0` 上梯、`t=3` 下梯，并在 `t=5` 完成门操作。
- 在 `t=5`，#2 与 #3 同时到达；先按 ID 登记两条请求，再处理 Ready。
- 电梯先服务 #2：从 3 楼空驶到 1 楼，`pickupTime=7`。
- #2 下梯并完成门操作时为 `t=14`，此时电梯位于 4 楼。
- #3 起点恰为 4 楼，因此 `pickupTime=14`（无需空驶）。
- #3 在 `t=18` 下梯，最后门操作在 `t=20` 结束。

### Sample 3 — 电梯长时间空闲

**Input**

~~~text
6 6 3 2
2
10 1 3
50 3 2
~~~

**Output**

~~~text
25 33 15
50 55 0
TOTAL_DISTANCE 8
FINISH_TIME 57
END_FLOOR 2
~~~

**Explanation**

- 电梯初始在 6 楼，直到 `t=10` 才收到 #1。
- 空驶 `|6-1|*3=15` 秒，`t=25` 到达 1 楼接客。
- `t=33` 抵达 3 楼，门操作到 `t=35`，随后空闲。
- #2 在 `t=50` 到达，恰好就在电梯当前楼层上梯。
- `FINISH_TIME=57`，包含最后的 2 秒送客门操作。

### Sample 4 — 输入并未按到达时间排序

**Input**

~~~text
5 1 1 1
3
10 5 4
0 1 2
0 2 3
~~~

**Output**

~~~text
12 14 2
0 2 0
3 5 3
TOTAL_DISTANCE 5
FINISH_TIME 15
END_FLOOR 4
~~~

**Explanation**

虽然 #1 在输入的第一行，但它直到 `t=10` 才到达；#2、#3 在 `t=0` 到达，所以服务顺序是 **#2 → #3 → #1**。

**输出仍然必须按 ID 1、2、3 的输入顺序排列。**

## 9. 必测边界场景

独立构造数据，检查以下情况：

1. `N=1`，电梯初始楼层恰好是第一位乘客的 `from`。
2. `N=1`，需要先空驶很远才能接客。
3. 请求在 `t=0` 到达。
4. 第一条请求在较晚时间才到达，电梯初始等待。
5. 两条请求同时到达，FIFO 按 ID 确定顺序。
6. 输入顺序与实际请求到达顺序不同。
7. 新请求在电梯**空驶去接客**时到达，不能抢占。
8. 新请求在电梯**载客行驶**期间到达，不能顺路载客。
9. 新请求在接客或送客门操作期间到达，只能排队。
10. 请求恰好在电梯 Ready 的时间戳到达。
11. 电梯完成送客开关门时已有多个等待请求。
12. 下一位乘客就在电梯的当前楼层，`pickupTime=readyTime`。
13. 两次服务之间存在很长空闲间隔。
14. 请求的 `from` 比 `to` 高（向下行驶）。
15. 交替上行、下行，多次空驶。
16. 区分 `dropoffTime` 与 `readyTime`，不能过早处理下一个乘客。
17. 总移动楼层数包含空驶，但不包含开关门耗时。
18. 累计完成时间超过 32-bit 整数范围。
19. `N=200,000`，确保程序能完成且事件顺序确定。
20. 所有请求服务完成、最后一次门操作结束后，模拟才终止。

## 10. OA 建模思考题（非题目规则）

写代码前先确认以下内容：

### State

- 电梯有哪些状态：`IDLE`、`GOING_TO_PICKUP`、`BOARDING`、`GOING_TO_DROPOFF`、`UNBOARDING`？
- 当前楼层在行驶期间是否需要持续更新？**本题的事件模型只要求在抵达楼层的事件中更新位置**；空驶/载客期间电梯不可再次派单，因此无需模拟每层经过的瞬间。
- 哪些数据属于电梯状态，哪些属于等待请求，哪些是结果统计？

### Events

至少考虑区分以下业务事件（名称可以自定）：

- `RequestArrival`：一个新请求抵达；
- `PickupArrival`：空驶结束，到达接客楼层；
- `DropoffArrival`：载客行驶结束，到达目标楼层；
- `Ready`：开关门结束，可接受下一条请求。

一条事件可以创建未来的事件。不能因为一条请求在输入中出现，就直接按输入顺序执行它。

### Ordering & Invariants

- 同一时间戳上，哪些事件先处理？
- 新请求能否改变已经安排好的接客/送客过程？
- 什么时候应从 FIFO 等待队列取出请求？
- `waitTime`、`pickupTime`、`dropoffTime` 的含义分别是什么？
- 所有请求是否最终恰好被接送一次？
- 电梯如何避免在两个任务上同时处于 Busy？
- 是否存在可能无限生成同一时间事件的情况？本题 `T,D≥1`，可用哪些事实证明终止？

### Implementation Strategy

题目鼓励 **Event-Driven / Discrete Event Simulation** 思路。

可以用一个按时间排序的事件容器，排序关键字首先是事件时间；同时间戳还需要遵守第 4 节规则。等待乘客的 FIFO 队列是**另一种逻辑容器**，不要与未来事件队列混淆。

本题不要求把整段模拟放进一个 Copy → Simulate → Validate → Commit 事务：**事件本身没有合法性拒绝 / 回滚需求**，直接修改 State 通常更简单。如果自行使用 TEDS 进行训练，不得改变请求的真实到达时间、不可抢占约束或事件优先级。
