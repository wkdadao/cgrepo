# 订单状态机工程设计

> 面向 OMS / SOR / Execution Engine（C++、异步 DMA / FIX）  
> 设计状态：讨论稿，供工程评审及与现有产品对比，并非特定 venue 的协议实现规范。  
> 核心思路：**可靠输入 + Event Buffer（Ingress Validation / Correlation / EventId Dedup / Ordering / Defer）+ Event Handler（领域校验 / Transition）+ 一致性提交 + 派生 Timer + Outbox + Reconciliation**。

## 1. 问题与目标

Execution Engine 的核心困难并非正常状态转换，而是异步外部世界的不确定性：

- New / Replace / Cancel 请求可能超时、迟到、重试、重复或结果未知。
- Fill 与 Cancel / Replace 响应可能发生竞态；终态以后仍可能收到相关事件。
- FIX/IPC 消息可能乱序；有的事件需要等待前置事实，可暂时 Deferred。
- DMA 崩溃或断线时，Engine 无法仅凭 IPC 发送成功判断 venue 是否接受请求。
- Engine 自己崩溃时，需要恢复订单事实、未决请求、Deferred Events、Timer 以及未完成 Side Effects。
- 回放与测试需要确定性；不能依赖状态机内部的真实时钟、真实 DMA 或真实 Timer。

设计目标：

1. **Correctness**：不重复应用成交；不静默丢弃可信的新事实；不把 Timeout 当成业务失败。
2. **Determinism**：相同 Snapshot + Event + 显式配置输入，生成相同结果。
3. **Recoverability**：已承诺接收的事件，不论何时崩溃都能证明已提交或可以重试。
4. **Single writer**：订单 Snapshot 只有一个明确的演化/提交路径。
5. **Low latency**：正常事件尽量走无额外拷贝、无队列分配的快速路径；异常路径可更重。
6. **Observability**：每个未正常应用事件都有明确 Result/Reason 和恢复出口。

**不追求**用一张 FSM 图覆盖所有外部不确定性，也不追求“所有异常都交给 Guard”。所有方案仍须适配真实 FIX dialect、DMA 交付保证和 venue 规则。

## 2. 总体架构与职责

~~~text
  DMA / FIX / Client Commands / Reconciliation / Timer
                       |
                       v
             Durable Journal / Inbox
               (可靠输入、重放)
                       |
                       v
                  Event Buffer
        ingress validate / correlate / EventId dedup
          ordering / deferred / retry / progress
                       |
                       v
              Domain Event Handler
          domain facts / ExecID / quantity
            switch(state):
              local policy / guard
              transition / fact update
                       |
                       v
      ProcessResult: after + actions + input progress
                       |
                       v
          Validate invariants & Commit
      (snapshot + input progress + deferred changes
             + domain outbox, logically atomic)
                       |
        +--------------+----------------+
        |              |                |
        v              v                v
  Timer Manager   Outbox Executor  Deferred Manager
   (derive only)     -> DMA         (retry/expiry)
        |              |                |
        +------ Events back to Journal <-+
                       |
                       v
              Reconciliation Manager
          (query/compare/repair by events)
~~~

| 组件 | 应当负责 | 不应负责 |
| --- | --- | --- |
| Adapter / Normalizer | FIX / venue-specific 消息转换为 Domain Event | 决定订单业务 Next State |
| Journal / Inbox | 可靠记录、顺序、重放与消费进度 | 决定订单状态 |
| Event Buffer | 通用 Ingress Validation、Order Routing/Correlation、EventId Dedup、排序、Defer 生命周期和进度 | 复制领域状态机、独立修改订单 Snapshot |
| Event Handler | 业务事实校验（ExecID / quantity / request response 语义）、State-specific Policy、Transition | 重复做输入 EventId 去重，或直接发送 FIX / 注册 Timer |
| Invariant Validator | 验证 before/after、聚合不变量 | 替代事件策略 |
| Repository | 原子提交状态、消费/Deferred 进度、Outbox | 根据真实时间改变业务语义 |
| Timer Manager | 从已提交 TimerSpec 注册/取消/恢复运行时 Timer | 决定 Cancel/New 成败 |
| Outbox Executor | 执行 SendNew/Replace/Cancel/Query，重试和回执跟踪 | 隐式修改 Order Snapshot |
| Reconciliation Manager | 从外部权威源查询、比较、生成修复事件 | 在 FSM 之外绕过提交路径写订单状态 |

原则：**逻辑职责分离不意味着一定拆成两个重复的 switch(state) 函数。** 能脱离订单业务事实判定的入口校验尽量由 Event Buffer 完成；依赖 Snapshot / Execution Ledger 或 venue 语义的校验仍由 Domain Handler 负责。局部 Policy、Guard、Transition 可相邻写在同一个 switch(state) 分支内。

## 3. 状态、事实和正常转移

### 3.1 简化订单状态

~~~cpp
enum class OrderState {
    PendingNew, Working, PartiallyFilled,
    PendingReplace, PendingCancel,
    Filled, Cancelled, Rejected
};
~~~

以下是**简化订单模型**，不是完整 FIX OrdStatus 语义：

| State | Event | Next State / 行为 |
| --- | --- | --- |
| PendingNew | NewAck | Working |
| PendingNew | NewReject | Rejected |
| Working / PartiallyFilled | Fill(full) | Filled |
| Working / PartiallyFilled | Fill(partial) | PartiallyFilled |
| Working / PartiallyFilled | RequestCancel | PendingCancel + SendCancel action |
| PendingCancel | Fill(partial) | 仍 PendingCancel；增加 CumQty |
| PendingCancel | Fill(full) | Filled；请求结果可能仍需追踪 |
| PendingCancel | CancelAck | Cancelled；撤销剩余量 |
| PendingCancel | CancelReject | 根据 CumQty 恢复 Working / PartiallyFilled |
| PendingReplace | ReplaceAck/Reject | 应用新版本 / 恢复或核对旧版本 |

> 单个枚举是一个简化。PendingCancel 和 “已经部分成交”可以同时成立；后者由事实字段表达。Replace 也可能与 Fill、Cancel 并发，生产模型需结合 venue 约束设计独立 PendingRequest 或正交状态。

### 3.2 事实字段与 Invariant

~~~text
OrderQty > 0
0 <= CumQty <= OrderQty                    // 未考虑 bust/correct 的简化模型
LeavesQty >= 0
Filled => CumQty == OrderQty
PendingCancel + partial Fill => 保留撤单在途事实
~~~

如果模型显式维护 CancelledQty，可以用内部守恒式：

~~~text
OrderQty = CumQty + CancelledQty + LeavesQty
~~~

**注意**：这只是本地内部数量分解。不要在 FIX 的所有 OrdStatus 上假设都存在对应的 CancelledQty 字段，也不要把本地计算的 LeavesQty 直接当作所有 venue 下发的 FIX LeavesQty 语义。

TradeBust / TradeCorrect 需要 Execution Ledger；单个 ExecutionId Set + 单调累加 CumQty 不足以覆盖修正成交。

## 4. Ingress Policy 与 Domain Policy 的边界

**一些 Event Validation、Correlation 和 Deduplication 适合放在 Event Buffer。** 划分依据不是谁先执行，而是该判断是否依赖订单领域事实、是否可以依据可恢复的输入身份独立判定。

### 4.1 责任矩阵

| 检查 | 推荐位置 | 原因及限制 |
| --- | --- | --- |
| FIX/SBE parse、schema、基本字段完整性 | Adapter / Event Buffer | 不依赖订单 Snapshot |
| Normalized Event 基本 Validation | Event Buffer | 基础 ID、枚举、长度、字段类型等 |
| OrderId / stream / session correlation | Event Buffer | 决定投递哪个 per-order owner；关联不明需隔离，不能当 Duplicate |
| **EventId 去重** | **Event Buffer** | 输入层稳定身份；依赖 durable Journal / Inbox / progress |
| 同 EventId，不同 payload | **Event Buffer → Conflict** | 比较来源与 payload fingerprint，不可简单丢弃 |
| Sequence gap / reorder | **Event Buffer** | 区分硬性协议顺序和可延期的语义依赖 |
| Event 的 Received/Deferred/Completed 进度 | **Event Buffer** | Deferred 仍然可重试，不等于业务已 Applied |
| generation / RequestId 初步路由 | Event Buffer | 判定业务上是否可忽略旧 generation 仍需 Domain |
| **ExecID 去重 / Bust / Correct** | **Domain Handler + Execution Ledger** | 同一成交可能以不同输入 EventId 重送 |
| Ack/Reject 与 pending request 对应 | Domain Handler | 需基于 Snapshot、RequestHistory、venue 语义 |
| Quantity、Overfill、LeavesQty / 版本约束 | Domain Handler | 属于业务事实与约束 |
| 是否 Defer、等待什么 prerequisite | Domain Handler 返回 Defer(reason) | Buffer 只管理 Defer 的保存、重试与 Deadline |
| State-specific Policy / Guard / Transition | Domain Handler | 放在同一个事件的 switch(state) 中 |
| Snapshot Invariants | Commit 前 Validator | 验证 before/after 和聚合约束 |

### 4.2 两类 Decision

Event Buffer 的入口结果可以是：

~~~cpp
enum class IngressDecision {
    Dispatch,             // 初次投递或恢复后可派发
    AlreadyCompleted,     // 同一输入已可靠处理
    AlreadyPending,       // 同一输入已在 Received/Deferred 中
    Invalid,
    UnresolvedCorrelation
};
~~~

Domain Handler 仍然支持：

~~~cpp
enum class EventResult { Applied, Duplicate, Ignored, Invalid, Defer, Conflict };
enum class DeferReason {
    WaitingForNewAck, WaitingForEarlierExecution,
    WaitingForRequestResult, WaitingForSnapshot
};
~~~

| Domain 结果 | 语义 | 提交/处理 |
| --- | --- | --- |
| Applied | 新业务事实/状态被应用 | 提交 Snapshot + Outbox + Event 完成进度 |
| Duplicate | 业务事实早已生效，如 ExecID 重复 | 不重复入账；可靠完成该输入 |
| Ignored | 已确认无需业务变化 | 可靠完成输入 |
| Invalid | 领域契约无效 | 保留审计或隔离 |
| Defer | 业务前置条件未满足 | 保存事件、原因、首次等待时间与 Deadline |
| Conflict | 业务事实互相矛盾或无法安全接受 | 保留证据，Reconciliation / 人工升级 |

**EventId 与 ExecID 去重不可混淆**：

~~~text
EventId E100, ExecID X1 -> Applied
EventId E101, ExecID X1 -> Domain Duplicate
EventId E100, payload changed -> Ingress Conflict
~~~

EventId 必须在明确的 source/session/order scope 下稳定。如果上游没有消息 ID，不能在每次重传时随机生成新的 UUID 并误以为实现了去重；应考虑可恢复的上游 ID、journal position 或定义明确的 transport identity，并确认跨重连的复用规则。

**Guard** 负责局部、无副作用的条件；**Invariant** 负责状态约束验证；**Reconciliation** 处理无法确定的事实。Event Buffer 不应自己实现另一张状态转移表。

### 4.3 终态事件处理案例

| 事件 | 处理原则 |
| --- | --- |
| Filled + 相同 ExecID 的 Fill | Duplicate |
| Filled + 新 ExecID 的 Fill | 可能 overfill / 事实冲突；不静默丢弃，核对 |
| Cancelled + 新 Fill | 新成交可能迟到、关联错或表示需修复；核对 |
| Filled + late CancelAck | 不抹去已确认 Fill；检查是否对应已知请求及 venue 语义 |
| Cancelled + CancelReject | 按 request ID 区分不同撤单请求；同一请求矛盾则核对 |
| Rejected + NewAck | 同 generation 下强冲突；核对 |
| PendingNew + Fill | 取决于上游顺序保证；接受、Defer 或核对，不能一概 Invalid |

“Fill 比 CancelAck 强”是一条有用直觉，**不是通用的消息优先级公式**。需要考虑来源可信度、业务含义、时间、bust/correct 以及 request identity。

## 5. Event Buffer：Ingress、Ordering、Deferred 与进度

Event Buffer 的通用 Validation / EventId Dedup 与 Domain Handler 的业务事实去重各有边界。**收到事件不等于完成处理，Deferred 事件也不能被输入级去重逻辑误杀。**

### 5.1 逻辑入口统一，物理 Hot Path 可优化

所有事件**逻辑上**先由 Event Buffer 协调；正常路径可以直接调用 Handler，只有真正需要延期的事件才入 Deferred Queue。无需为每个事件额外 heap allocation。

事件处理器返回 Defer 后：

~~~text
Event E1 -> tryApply(snapshot, E1) -> Defer(reason)
         -> durable deferred record + original event
Event E2 -> Applied + Commit
         -> retry E1 using NEW committed snapshot
         -> Applied / still Defer / Conflict
~~~

Deferred Queue **不是订单业务 State Machine 的子状态机**；它负责的是待处理输入的生命周期。但 “这个事件缺什么前置事实” 的领域判定仍由 Event Handler 给出，以免 Event Buffer 复制 FSM 转移表。

### 5.2 哪些事件允许越过 Deferred Event？

- **Protocol sequencing 严格**：不能随意越过 sequence gap，优先 resend/replay。
- **Semantic dependencies 可证明独立**：允许后续事件先提交，之后重试之前的事件。
- “当前无法 transition” 不是充分的 Defer 条件；需要明确缺失的 prerequisite 以及预期能补齐它的事件或权威查询。

### 5.3 Retry / Drain 算法

不是后台 busy loop；**新事件或相关 Snapshot 变化**触发局部 drain：

~~~text
New event committed
 -> scan relevant DeferredRecords in deterministic order
 -> if any Deferred successfully Applied, update snapshot/commit
 -> rescan possibly unblocked records
 -> stop on no progress or per-cycle work budget
~~~

限制单轮事件数/CPU budget，避免 deferred storm 饿死 hot path。若新事件并未使相关事实变化，可直接跳过无意义 retry。

### 5.4 Deferred Timer

~~~cpp
struct DeferredRecord {
    EventId eventId;
    Event original;
    DeferReason reason;
    Timestamp firstDeferredAt;
    Duration maxWait;
    uint64_t version;
};
~~~

Deadline 派生自 firstDeferredAt + maxWait。重复 retry **不能悄悄刷新 firstDeferredAt**。到期产生 DeferredExpired Event，经 Journal 进入 Event Buffer；它可能触发重新评估、Reconcile 或人工升级，但**不能未经核实直接删除真实 Fill**。

### 5.5 Deferred 与去重的关键交互

~~~cpp
enum class EventProgress {
    Received,     // durable ownership 已建立，业务未完成
    Deferred,     // 仍等待 prerequisite，未来需重试
    Applied,      // 业务效果和处理进度已提交
    Ignored,      // 已确认没有业务效果
    Conflict      // 持久化证据，等待核对
};
~~~

~~~text
E1 received -> Handler: Defer
   -> Durable DeferredRecord(E1) + firstDeferredAt + timeout

E1 redelivered with SAME EventId and SAME payload
   -> AlreadyPending，合并投递，不重复保存，不删除 E1

E2 received -> Applied + Commit
   -> Buffer retries existing deferred E1
   -> E1 bypasses FRESH ingress dedup of AlreadyPending
   -> Handler sees latest committed Snapshot
   -> Applied + Commit (Snapshot + E1 completion + Deferred removal)

E1 redelivered AFTER completion
   -> AlreadyCompleted，不再调用 Handler

E1 received with SAME EventId but DIFFERENT payload
   -> Ingress Conflict，保留原始证据
~~~

建议提供不同入口：

- **onIncoming**：首次/重复投递时验证输入身份与 payload fingerprint；区分 AlreadyCompleted、AlreadyPending、Dispatch。
- **retryDeferred**：使用原始 EventId 和已持久化原始事件再次调用 Domain Handler；不可被普通输入去重拦截为 AlreadyPending。
- **commitProgress**：Event 的 Applied/Finished 进度与 Snapshot、Outbox 及 DeferredRecord 完成标记一致性提交。

可使用 Journal + Checkpoint + Durable Deferred Index，而不一定为每个输入创建独立数据库行。**不能只推进一个最大 sequence number，除非此前每个事件都已完成或被 durable deferred 接管。**

## 6. Request Timeout、Retry 与 Pending Watchdog

New / Replace / Cancel 可以复用 PendingRequest 生命周期模型：

~~~cpp
enum class RequestType { New, Replace, Cancel };
enum class RequestPhase {
    AwaitingResponse, RetryPending, Reconciling, Completed
};
struct PendingRequest {
    RequestType type;
    RequestId id;
    uint64_t generation;
    uint32_t attempt;
    uint32_t retryCount;
    RequestPhase phase;
    Timestamp startedAt;    // 持久化时间锚点
    Duration attemptWait;   // 本 attempt 的等待预算
    Duration overallWait;   // 整个 request 的上限，可选
};
~~~

核心语义：

- Timeout = 本地在期限内没有得到确定结果；**不是** exchange Reject，也**不是** Cancel 失败。
- retry 是否安全取决于 venue、ClOrdID、FIX session、DMA 去重和已知发送状态。
- 原 New 可能已被接受，不能随意用新 ID 重发。
- Replace 可能已改变 venue 工作参数；Cancel 期间仍可能继续 Fill。
- attempt 重试不要无限延后 request 的 overall deadline。
- 非终态不等于异常：Working/PartiallyFilled 可以长期存在；应监控**未决操作时长**，而不是所有订单的 state age。

建议按 PendingRequest ID/attempt/generation 做统一 watchdog；正常路径不需要大量分散的 ScheduleNewTimer / ScheduleCancelTimer Actions。

## 7. Timer：从已提交数据自动派生

### 7.1 不在状态机中直接调用 Timer

~~~text
RequestCancel
 -> Handler produces after PendingCancel(startedAt, timeout)
                     + SendCancel outbox action
 -> Atomic Commit
 -> TimerManager.sync(committed before, committed after)
 -> Outbox dispatcher sends to DMA
~~~

**Timer 注册是运行时资源；PendingRequest + time anchor + configured duration 才是可恢复的数据。**

对于 Deferred Event，Timer 从 Durable DeferredRecord 派生；两个业务语义可以共用底层 TimerService，但不要强行合并业务状态机。

### 7.2 相对时间与确定性

“绝对 deadline 不利于 replay”并不严格成立；真正的问题是 reducer 内部调用 now() 或读取变化后的配置。

推荐存储：

~~~cpp
struct TimerSpec {
    TimerId id;            // order/request/generation/attempt/kind/version
    Timestamp startedAt;  // UTC/可跨重启解释的逻辑时间锚点
    Duration delay;       // 创建时固定使用的配置值
};
Timestamp deadline(const TimerSpec& t) {
    return t.startedAt + t.delay;
}
~~~

- Event Handler 只使用显式注入且已 journal 化的 acceptedAt / 配置值。
- 处理重放时同一批输入不能读取新的 timeout 配置值。
- Timer Service 的实际计时可以使用 monotonic clock；持久化时间锚点应支持跨重启比较，并明确系统时钟调整的容错策略。
- 对 Partial Fill 等无关状态改变，deriveTimers(before) == deriveTimers(after)，不重置 cancel deadline。

### 7.3 Timer 到期产生普通事件并写 Journal

~~~cpp
struct RequestTimeout {
    OrderId orderId;
    RequestId requestId;
    uint64_t generation;
    uint32_t attempt;
    TimerKind kind;
    uint64_t timerVersion;
    Timestamp scheduledDeadline;
};
~~~

~~~text
Timer expired -> append RequestTimeout to Journal
             -> Event Buffer
             -> Handler validates current TimerId
             -> transition (retry-count / phase) + actions
             -> Commit
~~~

旧 Timer 即使到期、取消失败、被重复投递，也不能改变已经完成的 Request。**TimerId + phase + journal/committed progress** 必须保证最多一次有效的状态与外部 action 效果（通常通过幂等实现，而不是要求零重复投递）。

### 7.4 过期 Timer 重复生成的防护

Crash 可能发生在 Timer 到期与 Journal append 之间：

- append 已提交，处理尚未提交：Recovery replay 现有 Timeout。
- append 结果未知：Recovery 可能重新生成相同 TimerId 的 Timeout。
- 未 append：Recovery 依据已提交 TimerSpec 补生成。

因此应有**稳定 TimerId 和持久化的处理/消费进度**，并让 Timer Timeout 处理幂等。Timeout transition 应推进 attempt/phase 或 reconcile status，避免相同过期 deadline 无限重复生产副作用。

## 8. C++17 接口草图：Ingress Filter + Domain Handler

> 以下是控制流草图，外围 Event/Repository/Action 等类型和 helper 均省略，**不能直接当作独立可编译程序**。目标是避免在 Buffer 和 Handler 中重复同一类检查。

~~~cpp
enum class EventResult { Applied, Duplicate, Ignored, Invalid, Defer, Conflict };

struct ProcessResult {
    EventResult result;
    std::optional<Snapshot> after;
    std::vector<Action> actions;   // durable outbox intentions
    DeferReason deferReason{};
};

class DomainEventHandler {
public:
    ProcessResult tryApply(const Snapshot& before, const Event& event) const {
        return std::visit([&](const auto& e) {
            return onEvent(before, e);
        }, event);
    }

private:
    ProcessResult onEvent(const Snapshot& before, const Fill& e) const {
        // Buffer 已校验输入格式、Order 路由、EventId。
        // 业务 ExecutionId 和事实一致性仍由领域层维护。
        if (executionLedger_.contains(e.executionScope, e.execId))
            return duplicate();

        switch (before.state) {
        case OrderState::Working:
        case OrderState::PartiallyFilled:
        case OrderState::PendingCancel: {
            if (e.qty > before.remainingExecutableQty()) return conflict();
            Snapshot after = before;
            const bool cancelling = before.state == OrderState::PendingCancel;
            after.recordExecution(e); // 与快照/进度保持原子持久化
            if (after.isFullyFilled()) after.state = OrderState::Filled;
            else if (!cancelling) after.state = OrderState::PartiallyFilled;
            return applied(std::move(after));
        }
        case OrderState::PendingNew:
            return defer(DeferReason::WaitingForNewAck); // 仅适用明确协议依赖
        default:
            return conflict(); // 新 ExecID 的终态 Fill 不能静默忽略
        }
    }

    ProcessResult onEvent(const Snapshot& before,
                          const RequestTimeout& e) const {
        if (!matchesActiveTimer(before, e)) return ignored();
        switch (before.pendingRequest->phase) {
        case RequestPhase::AwaitingResponse: {
            Snapshot after = before;
            if (safeToRetry(before.pendingRequest.value())) {
                after.advanceRetryAttempt();
                auto action = makeRetryAction(after);
                return applied(std::move(after), {std::move(action)});
            }
            after.markReconciling();
            auto action = makeReconcileAction(after);
            return applied(std::move(after), {std::move(action)});
        }
        default:
            return ignored();
        }
    }
    const ExecutionLedger& executionLedger_;
};

class OrderEventBuffer {
public:
    void onIncoming(const InputRecord& input) {
        // 初次输入和重投递：校验、Order correlation、
        // EventId + payload fingerprint、progress。
        auto decision = ingressPolicy_.check(input, progress_);

        switch (decision) {
        case IngressDecision::AlreadyCompleted: return;
        case IngressDecision::AlreadyPending:   return;
        case IngressDecision::Invalid:
        case IngressDecision::UnresolvedCorrelation:
            persistIngressAnomaly(input, decision);
            return;
        case IngressDecision::Dispatch:
            dispatchOwned(input);
            return;
        }
    }

    // Deferred 不是新输入；不能被 AlreadyPending 入口规则挡住。
    void retryDeferred(const DeferredRecord& deferred) {
        if (progress_.isCompleted(deferred.eventId)) return;
        dispatchOwned(deferred.originalInput);
    }

private:
    void dispatchOwned(const InputRecord& input) {
        auto result = handler_.tryApply(snapshot_, input.event);
        switch (result.result) {
        case EventResult::Applied:
            commitSnapshotProgressLedgerAndOutbox(result, input);
            retryRelevantDeferredAfterCommit();
            break;
        case EventResult::Defer:
            durableDeferAndRecordProgress(input, result.deferReason);
            break;
        case EventResult::Duplicate:
        case EventResult::Ignored:
            commitInputCompletion(input);
            break;
        case EventResult::Invalid:
        case EventResult::Conflict:
            persistAnomalyAndEscalate(input, result);
            break;
        }
    }
    IngressPolicy ingressPolicy_;
    DomainEventHandler& handler_;
    // snapshot_, progress_ 由单 order owner 维护。
};
~~~

**实现警示**：

1. 同 EventId 不同 payload 不能只因 key 已存在而返回 AlreadyPending；需检测 fingerprint 和来源范围。
2. 同 ExecID 不同 EventId 的 Fill 仍可能是 Duplicate；ledger 必须有可恢复的事实依据，并正确处理 Bust/Correct。
3. Buffer 的 progress 不能只存内存 Set；Received、Deferred、Applied 等状态必须能从 Journal/Inbox 和持久进度重建。
4. Retry Deferred 要绕过**新事件输入级**去重，但仍检查已完成状态以消除重放竞态。
5. 业务 Ledger 更新、Snapshot 更新、Event 完成进度、Deferred 删除和 Outbox 必须属于同一逻辑提交边界。
6. 业务依赖明确才允许 Defer；Terminal Fill、late Ack、RequestId/generation 异常必须 case-by-case 处理。
7. 生产实现可以用 per-order owned mutable state、COW 或增量 journal 减少大 Snapshot 拷贝；**Commit 前不能发不可逆 Side Effect**。
8. Filled 后仍需保留已完成 RequestHistory 以关联可能迟到的 CancelAck/CancelReject。

## 9. Journal、持久化与 Crash Consistency

### 9.1 Event Buffer 不必整体持久化

- **Buffer 本体可以纯内存**。
- Event Journal / reliable inbox / durable deferred store 必须足以恢复所有尚未安全完成的事件。
- 没有可靠 replay 的 DMA IPC，Defer 前就需要建立 durable ownership；不可在只放进内存 queue 后确认原消息消费完成。
- 已 Apply 的 Execution 要么持久化稳定去重/ledger，要么能从完整 journal 正确重建。
- EventId Dedup 索引可以是内存缓存，但其可靠结果和 processing progress 必须从 Durable Inbox/Journal/Checkpoint 恢复。
- Deferred 在业务上仍未完成；同 EventId 重投递只合并投递，不能清除 DeferredRecord；retryDeferred 可再次进入 Domain Handler。
- 同 EventId 不同 payload 应持久记录冲突，而不是只按 ID 视为正常重复。

### 9.2 单个逻辑 Commit Boundary

~~~text
A. Receive/append input event durably
B. Event Buffer ingress validate / correlate / EventId dedup / ordering
   -> tryApply -> after + actions / defer / anomaly
C. Commit:
     - Order Snapshot
     - EventId completion / input sequence / durable processing progress
     - Deferred record create/complete
     - Outbox intents
D. After Commit:
     - TimerManager.sync / recover
     - OutboxDispatcher.notify
     - Deferred retry
~~~

必须支持 Crash 后判断每个已承诺的输入：

~~~text
Committed Applied
    OR
Durably Deferred
    OR
Replayable From Journal
~~~

如果只能实现不同数据库间的非原子写入，需要引入明确的原子边界、幂等写入、WAL/checkpoint 或其他等效恢复协议。**Snapshot + Outbox 事务并不能自动保证 DMA/FIX 的 exactly-once 外部送达。**

### 9.3 DMA Crash 场景

~~~text
Engine commits PendingNew + Deadline + SendNew(outbox)
DMA may:
  - never consume it
  - consume but not send
  - send FIX but crash before reporting
  - venue accepts but response is lost
Engine cannot infer which from "no ACK".
~~~

因此端到端 RequestTimeout 表示 *outcome unknown*。如果 DMA 无发送状态回执，不应虚构 “DMA delivery timeout = venue response timeout” 的精确拆分。

RetryNew / RetryCancel 必须遵守 venue/FIX identity 与查询能力要求。

## 10. Historical Replay 与 Live Recovery

| 维度 | Historical Replay | Crash Recovery |
| --- | --- | --- |
| 目标 | 重建历史决策/状态 | 恢复当前未完成工作 |
| 时间 | Journal 中记录的时间/顺序 | 真实当前时钟 + 持久化锚点 |
| Timer | 不真实注册历史 Timer；重放已记 Timeout | 由 committed TimerSpec 重建 |
| Outbox | 不真实重发历史 FIX | 恢复未完成意图并核对是否安全发送 |
| Ordering | 按有保证的 per-order Journal 顺序 | 补齐 durable 输入后恢复串行执行 |
| Reconcile | 可模拟/重放结果事件 | 必要时查询真实权威源 |

仅有相对 timeout + startedAt **不能保证历史事件顺序的确定性**。若 Timeout 会改变状态，应记录 Timeout Event（或另有严格可重现的虚拟时钟调度顺序），否则当 Ack 与 Timeout 接近时，重放可能得到不同结果。

重启恢复建议顺序：

1. 加载 last committed snapshot + journal checkpoint；
2. 恢复未完成事件/Deferred records/outbox；
3. 补 replay 外部事件与已记录 Timeout，恢复 per-order 顺序；
4. 重建剩余 TimerSpec；已到期且尚未处理的 Timer 形成带稳定 TimerId 的 Timeout Event；
5. 对仍无法确定外部结果的 PendingRequests 安排 Reconciliation；
6. 恢复 live dispatch。

顺序需要根据系统的输入串行化、session replay 和权威消息可用性调整；**不要同时由 recovery timeout 与 outbox 各自盲目重发同一请求**。

## 11. Reconciliation 触发与职责

建议统一创建 ReconcileRequest，而不是在 guard 中直接查询 DMA：

| 场景 | 优先处理 | 何时 Reconcile |
| --- | --- | --- |
| Filled 后新的、非重复 Fill | 保护事实、记录冲突 | 及时核对 |
| Reject / Ack 互相矛盾 | correlation、generation 核验 | 无法解释时 |
| New/Replace/Cancel Timeout | 检查 pending、retry 安全性 | 首次 timeout 或安全重试耗尽，取决于 venue |
| Deferred 超期 | 重新评估 prerequisite | 仍缺事实时 |
| FIX sequence gap | session resend/replay | replay 无法补齐时 |
| DMA disconnect / restart | 恢复输入和发送状态 | 受影响未决请求结果仍未知时 |
| Engine crash / restart | journal replay + 恢复计时 | 未决外部效果无法判断时 |
| 长期 Working | 验证 TimeInForce / session / 客户意图 | **不能只因非终态时间长就触发** |
| Periodic audit | 低频采样与比较 | 检测到不一致时 |

Reconciliation 结果也应转为可审计的事件，通过相同 Order Owner/Commit Boundary 处理。Status Request 的权威性因 venue 而异，单次 OrderStatusResponse 未必涵盖所有成交，必要时结合 drop-copy、execution ledger、交易后数据和人工判断。

同一订单并发多个 ReconcileRequest 要去重/合并；故障大面积发生时要限流与退避。

## 12. 多层约束（不是单纯的执行顺序）

~~~text
External authoritative evidence
System/parent-child consistency
Order facts & correlation
Object invariant
Event policy (duplicate / late / defer / conflict)
Transition guard
State transition graph
~~~

它们是不同**约束范围和解释能力**，不是严格全序“谁永远覆盖谁”。例如真实 execution 必须得到保护，但一个时间更晚、来源更弱的状态报告未必能直接覆盖已知 execution ledger。更高层冲突由 Reconciliation 解决。

## 13. 质量评测与测试矩阵

### 13.1 Correctness / Failure Injection

| 注入点或事件顺序 | 必须验证 |
| --- | --- |
| Commit 前 crash | 没有未经提交的外部发送或状态可见 |
| Commit 后、Timer 注册前 crash | Deadline 可恢复 |
| Commit 后、Outbox 发送前 crash | 既不丢指令，也不产生不可控重复 |
| DMA 已 send FIX、未上报时 crash | 结果 Unknown；禁止不安全 RetryNew |
| Timer 到期与 Ack 同时发生 | 以 Journal/Commit 顺序为准；旧 Timer 忽略 |
| Timeout append 已成功、处理前 crash | Replay 后至多一次业务效果 |
| Timeout append 成功但确认丢失 | 稳定 TimerId 避免重复效果 |
| Partial Fill during PendingCancel | CumQty 增加，PendingCancel 保留 |
| Duplicate Fill（不同 EventId、相同 ExecID） | Domain Ledger 判重复；单 ExecID 一次入账 |
| 相同 EventId + 相同 payload 重投递 | AlreadyPending 合并或 AlreadyCompleted 忽略，不二次业务应用 |
| 相同 EventId + 不同 payload | Ingress Conflict；记录证据，不能静默跳过 |
| E1 Deferred 后相同事件重新投递 | 不因输入去重错误删除 E1，也不产生第二条 DeferredRecord |
| E1 Deferred → E2 Applied → retry E1 | retryDeferred 绕过新输入 AlreadyPending 拦截，并能正常推进 |
| Snapshot 已更新、Event 进度尚未提交时 Crash | 必须由原子边界或幂等恢复协议消除不一致 |
| Filled + new Fill | 不静默丢弃，保留异常证据 |
| Deferred E1、随后 E2 补齐条件 | E1 被重试并提交，或最终明确升级 |
| Deferred 长期无新 Event | Deadline 仍能触发升级 |
| Apply deferred 后、删除 record 前 crash | 不重复改变交易事实 |
| Historical Replay | 不真实执行 DMA/Timer，并且结果可复现 |
| Clock jump / config change | 已存在 pending request 的 deadline 语义稳定 |
| 多 order 高峰 / deferred drain | bounded work，不饿死 hot path |

### 13.2 性能与运维

- 按 New/Replace/Cancel/Fill 分开测 p50、p99、p99.9、max。
- 覆盖 burst、queue backlog、recovery、deferred drain、大量 timer 同时过期。
- 统计 IngressDecision / Domain EventResult / Reason 分布、EventId 重投递率、同 ID payload 冲突、Deferred queue 深度与 age、pending age、reconcile backlog、outbox age、timeout scheduler lag。
- 为每个请求记录 OrderId、RequestId、generation、attempt、TimerId、journal offset、commit version；使跨 Engine/DMA/FIX 的故障可以追踪。
- 对 per-order 所有修改维持单 owner / 串行提交；如果跨线程共享则需要版本/CAS 或等效事务保护。

## 14. 工程评审清单

- [ ] State-specific Policy 和 Transition 是否在同一事件分支相邻维护，避免双重 switch？
- [ ] Guard 是否无副作用？是否藏着 DMA send、数据库写入或 schedule timer？
- [ ] 是否明确区分 Ingress Validation/Correlation/EventId Dedup 与 Domain ExecID/业务事实校验？
- [ ] EventId 和 ExecID 是否各自定义身份 scope 和稳定持久化来源？
- [ ] 相同 EventId 的不同 payload 是否会被识别为冲突？
- [ ] Deferred retry 是否能绕过新输入 AlreadyPending 拦截，同时避免重复完成？
- [ ] 是否区分 Received、Deferred、Applied、Ignored、Conflict 的持久化进度语义？
- [ ] 是否区分 Duplicate / Ignored / Invalid / Defer / Conflict？
- [ ] Deferred 的 prerequisite 是否显式可解释且有超期出口？
- [ ] Deferred 能否安全越过其他事件？严格 sequence gap 如何处理？
- [ ] Journal/Inbox、Snapshot、Deferred Progress、Outbox 是否形成正确的提交语义？
- [ ] 每个已承诺接收的 Event 崩溃后是否 Applied / Durably Deferred / Replayable？
- [ ] New/Replace/Cancel Timeout 是否统一按 RequestId/generation/attempt 校验？
- [ ] RequestTimeout 和 DeferredExpired 是否经过 Journal，可重放、幂等？
- [ ] Timeout 配置是否在请求创建时固定，重试是否有 overall deadline？
- [ ] Timer 是否从 committed Snapshot / Durable DeferredRecord 派生，能够在 Crash 后重建？
- [ ] 已完成 request 的 correlation 历史是否保留以解释 late Ack/Reject？
- [ ] DMA 未反馈发送进度时，是否避免假设 venue 已收到？
- [ ] Timeout、Replay、Recovery、Reconciliation 是否在统一 per-order commit 边界收敛？
- [ ] 是否有故障注入、消息顺序排列、property-based、replay 与 tail latency 测试？

## 15. 最终结论

**推荐折中方案**：

1. **Event Buffer** 负责通用 Ingress Validation、Correlation、EventId Dedup、Ordering、Deferred 生命周期及 Event Progress；本体可以纯内存，但所依据的状态/输入必须可靠恢复。
2. **Event Handler** 负责 ExecID/Execution Ledger、Request response 和数量等领域事实，State-specific Policy/Guard 与 Transition 放在同一个 switch(state) 内。
3. **State Machine / Reducer** 是订单 Snapshot 正常演化的唯一作者。
4. **Timer** 从已提交的 PendingRequest 或 DeferredRecord 的时间锚点 + 相对 Timeout 自动派生；不在状态机中直接启动真实 Timer。
5. **Timeout Event** 像普通事件一样进入 Journal，再按确定顺序处理；迟到、重复、重启后补发均需可幂等。
6. **Outbox** 执行外部 DMA/FIX Side Effects；发送结果不确定时按真实协议核对，不能将 Timeout 当成 Reject。
7. **Reconciliation** 是事实冲突与长期不确定性的安全出口，但不应成为所有 Guard False 的默认处理。

最终以三条系统不变量验收：

> **Input durability**：每个已承诺接收的事件都已提交、可靠延期，或可以重放。  
> **Commit consistency**：Snapshot、事件进度、Deferred 状态和 Outbox 在同一逻辑提交边界一致。  
> **Timer recoverability**：所有仍有效 Timer 均可从已提交数据重建，重复/迟到 Timer 不产生重复业务效果。
